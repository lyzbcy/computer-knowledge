云原生基础运维

基于《云原生基础运维手册》（2026-07-19）深度拆解 · 受众：Java 后端开发管培生（带你理解服务跑在哪、为什么这样部署）

01 学习目标与阅读路径

作为 Java 后端，你写的服务最终要部署成 Pod 跑在 K8s 上。这一章带你理解部署背后的基础设施。学完你应该能做到：

1
区分虚拟机 vs 容器——容器共享宿主机内核、毫秒级启动、MB 级资源；虚拟机各自独立 OS、分钟级启动、GB 级资源。能说出为什么公司选容器。
2
背出 K8s 集群双层结构——Master Node（控制平面：调度/期望状态/配置存储）+ Worker Node（运行 Pod/容器、汇报状态）。
3
记住公司命名空间划分——系统命名空间（kube-system/monitoring/traefik 等）vs 业务命名空间（wshoto/wshoto-gray/wshoto-middleware/wshoto-monitor/wshoto-plugin）vs 工具命名空间（tools）。
4
分清 Pod / Deployment / Service / Ingress 职责——Pod 是最小部署单元、Deployment 管无状态应用副本/滚动更新、Service 给 Pod 稳定入口、Ingress 做七层域名路由。
5
把 K8s 和框架泳道对应起来——生产命名空间 wshoto 的实例 metadata laneId=MASTER；灰度命名空间 wshoto-gray 的实例 laneId=GRAY，对应第8章 lane-boot-starter。

阅读路径：补容器/编排背景 → 理解 K8s 核心对象 → 公司集群落地（命名空间/Service 类型）→ Pod 生命周期与故障排查 → 复盘。

02 零基础背景包

背景补充 1：为什么需要容器

背景补充

源代码部署的痛点：开发、测试、生产环境因系统/依赖版本不同容易出 bug（「在我机器上能跑」）。容器把应用+依赖打包成镜像，一次构建处处运行，环境一致性极强，部署速度从「编译→装依赖→改配置→启动」简化为「拉镜像→启容器」。

为什么读本文需要它：理解容器价值，才能理解为什么公司整套云原生基础设施都建立在 Docker + K8s 上。

背景补充 2：编排问题的本质

背景补充

容器一两个时人工能管；几十上百个跨多台机器时，就遇到：哪台机器还有资源？容器挂了谁来重启？怎么滚动更新不停服？怎么让调用方找到漂移的容器？K8s 就是来解决这些「编排」问题的。

为什么读本文需要它：K8s 的每个核心对象（Deployment/Service/Ingress）都对应一个编排痛点。

背景补充 3：声明式 vs 命令式

背景补充

K8s 是「声明式」：你写 YAML 描述「我想要 3 个 Pod 副本」，K8s 控制平面持续把实际状态往期望状态拉。如果某个 Pod 挂了，控制器发现实际只有 2 个，会自动再创建 1 个。这和「命令式」（手动启停）思维完全不同。

为什么读本文需要它：理解「期望状态」「控制器」这些词，才看得懂 Deployment、DaemonSet 在做什么。

背景补充 4：服务发现与框架呼应

背景补充

第8章讲 discovery-nacos-boot-starter：服务启动时把自己注册到 Nacos，调用方查 Nacos 拿实例列表。K8s 自己也有 Service + DNS 做集群内服务发现。公司混用：业务服务走 Nacos（支持多环境灰度路由），基础设施走 K8s Service。

为什么读本文需要它：Service 这节会反复和第8章 discovery 对比。

03 原文问题定位

表面在讲什么？

容器技术、Docker、K8s（集群/命名空间/Pod/控制器/Deployment/Service/Ingress/ConfigMap/Secret）+ 运维实战（故障排查/扩缩容/配置变更）+ 多环境隔离分流。

深层在回答什么问题？

「公司的 Java 微服务最终跑在什么样的基础设施上？为什么是这套？」

答案是「容器化交付 + K8s 编排 + 命名空间隔离 + Service 抽象」：原文：K8s 是用于自动部署、扩缩容和管理容器化应用的编排平台，适合统一管理多节点、多服务和多实例的生产环境。

作者为什么要写这篇？

这是面向运维和开发的入门手册，目的是统一云原生基础认知，让开发理解服务部署链路、让运维有标准化排查路径。手册特别强调公司集群的真实命名空间划分和 Pod 示例，不是抽象 K8s 教程。

只记一个问题

「我写的 Java 服务怎么从源码变成生产流量？」——代码打成镜像 → K8s 用 Deployment 管副本 → Pod 跑容器 → Service 给稳定入口 → Ingress 接外部域名 → ConfigMap/Secret 注入配置。

04 原文结构地图

原文结构类型：机制流程 + 概念层级（从底层容器到上层 K8s 对象，再到运维实战）

核心：容器化交付 + K8s 编排 + 公司命名空间隔离
第1层：容器技术基础（1.x）
容器=轻量级虚拟化（操作系统级）；vs 虚拟机（硬件虚拟化）
第2层：Docker 容器引擎（2.x）
应用+环境打包成镜像，以容器方式交付运行，提高一致性/可移植性/效率
第3层：K8s 集群核心对象（4.x）
Cluster（Master+Worker）→ Namespace（系统/业务/工具）→ Pod（最小部署单元，单容器/多容器边车）→ Controller（Deployment/StatefulSet/DaemonSet/Job/CronJob）→ Deployment（副本/滚动/回滚/扩缩）→ Service（ClusterIP/NodePort/LoadBalancer）→ Ingress（域名/路径/TLS）→ ConfigMap（非敏感配置）→ Secret（Base64 敏感信息）
第4层：运维实战（5.x）
查看集群/应用状态、Pod/Service 故障排查、更新镜像/配置、扩缩容
第5层：多环境隔离分流（6.x）
wshoto（生产 MASTER）+ wshoto-gray（灰度 GRAY）+ wshoto-middleware（中间件）+ wshoto-monitor（监控）+ wshoto-plugin（插件）
节点关系说明：5 层是由下到上的依赖堆叠。容器是原子，K8s 编排容器，Namespace 切分集群，Pod/Deployment/Service 等对象定义「跑什么/怎么跑/怎么找到」，最后多环境用命名空间 + laneId 双重隔离。

05 核心判断与依据

判断1：容器 vs 虚拟机的本质差异是虚拟化层级

原文依据：原文：虚拟机=硬件虚拟化、每个 VM 独立 OS、分钟级启动、GB 级；容器=操作系统虚拟化、共享宿主机 OS 内核、毫秒级启动、MB 级

特性虚拟机 VM容器 Container
架构硬件虚拟化操作系统虚拟化
OS每个 VM 独立 OS共享宿主机 OS 内核
启动时间分钟级毫秒级
资源占用GB 级MB 级
密度单机数十个单机数百上千个

判断2：K8s 集群是 Master + Worker 双层

原文依据：原文 4.1.2/4.1.3：Master Node 负责管理整个集群，主要承担调度 Pod、维护期望状态、存储配置；Worker Node 负责运行实际的业务应用，运行 Pod 和容器、向 Master 汇报状态

节点职责
Master Node（控制平面）接收操作请求、调度 Pod、维护期望状态、存储配置、监控节点和应用状态
Worker Node（工作节点）运行 Pod 和容器、执行调度任务、管理本节点容器生命周期、提供网络和服务访问、向 Master 汇报状态

判断3：公司命名空间分系统/业务/工具三类

原文依据：原文 4.2.2：命名空间分类——系统命名空间（kube-system/monitoring/observability/traefik 等）、业务命名空间（wshoto/wshoto-gray/wshoto-middleware/wshoto-monitor/wshoto-plugin）、工具命名空间（tools）

  • 系统命名空间：kube-system（CoreDNS/CSI）、monitoring（Prometheus/Grafana）、observability、traefik（Ingress 控制器）、operator-lifecycle-manager、tekton-pipelines（CI/CD）
  • 业务命名空间：wshoto（生产 MASTER）、wshoto-gray（灰度 GRAY）、wshoto-middleware（MySQL/Redis/Kafka/Nacos）、wshoto-monitor（业务监控）、wshoto-plugin（插件）
  • 工具命名空间：tools（Kafdrop、RocketMQ 控制台）

判断4：Pod 是最小部署单元，公司暂未用边车模式

原文依据：原文 4.3.1/4.3.2：Pod 是 Kubernetes 中最小的部署单元，包含一个或多个容器，这些容器共享网络和存储；公司集群的 POD 暂未使用多容器（边车模式）

类型：事实。公司当前 Pod 都是单容器模式（一个 Java 服务一个 Pod），未用边车。

判断5：Deployment 管「副本+滚动+回滚+扩缩」四件套

原文依据：原文 4.5：Deployment 是最常用的控制器，用于管理无状态应用，提供滚动更新、回滚、扩缩容等能力

能力说明
副本管理维持期望数量的 Pod 实例
滚动更新逐个替换旧版本 Pod，不停服
版本回滚出问题时回退到历史版本
扩缩容手动或自动增减副本数

判断6：Service 三种类型对应不同访问场景

原文依据：原文 4.6：Service 是 Kubernetes 中的服务发现机制，为 Pod 提供稳定的访问入口。本集群使用的 Service 类型：ClusterIP（集群内部访问）/ NodePort（节点端口暴露）/ LoadBalancer（云负载均衡器）

类型访问方式使用场景
ClusterIP（默认）ClusterIP + DNS内部服务通信
NodePortNodeIP:NodePort临时测试、开发环境
LoadBalancer外部 IP生产环境对外服务

判断7：Pod phase 五状态不是固定流转

原文依据：原文 4.3.3：Pod 的 phase 是对其生命周期阶段的高层概括，并不是一套固定的状态流转流程

Phase说明
Pending已被接受，等待调度/拉镜像/创建容器
Running已绑定节点，容器已创建，至少一个在运行/启动/重启
Succeeded所有容器成功终止，不会重启
Failed所有容器终止，至少一个失败，不会重启
Unknown无法获取状态，通常与所在节点通信异常

易误读：不是 Pending→Running→Succeeded 的线性流转，是高层概括。

06 关键概念拆解

概念1：Pod（最小部署单元）

原文术语：Kubernetes 中最小的部署单元

人话解释：Pod 是 K8s 调度的最小单位，里面装一个或多个容器（公司当前都是单容器 Pod）。同一个 Pod 内的容器共享网络和存储。Pod 是临时的——挂了不会自我修复，由控制器（Deployment）重新创建。

你写的 wshoto-customer Java 服务，最终就是以一个 Pod 的形式跑在 Worker Node 上。Pod 里的容器就是你的 Java 进程（来自镜像）。Pod IP 是临时的，重启就变。

与其他概念的关系：Pod 是 Deployment 管理的对象；Service 通过 Label Selector 找到一组 Pod。

原文 4.3

概念2：Deployment（无状态应用控制器）

原文术语：管理无状态应用，提供滚动更新/回滚/扩缩容

人话解释：Deployment 是「期望状态守护者」。你声明「我要 3 个 wshoto-customer 副本」，Deployment 持续保证实际有 3 个 Pod 在跑；某个挂了它自动再建一个。要升级版本时，它逐个用新 Pod 替换旧 Pod（滚动更新），出问题能回滚。

与其他概念的关系：Deployment 管 Pod；StatefulSet 管有状态应用（数据库）；DaemonSet 每个节点跑一个（日志采集）；Job/CronJob 一次性/定时任务。

控制器用途场景
Deployment无状态应用Web/API 服务（你的 Java 服务）
StatefulSet有状态应用数据库、消息队列
DaemonSet每节点一个日志采集、监控代理
Job一次性任务数据迁移、批处理
CronJob定时任务备份、清理、报表

原文 4.4.2

概念3：Service（稳定访问入口）

原文术语：服务发现机制，为 Pod 提供稳定的访问入口

人话解释：Pod IP 是临时的（重启就变），调用方不能直接记 Pod IP。Service 在一组 Pod 前面加一个稳定的虚拟 IP + DNS 名，自动负载均衡到后端 Pod。无论 Pod 怎么生死，Service 入口不变。

假设 wshoto-customer 有 3 个 Pod（IP 分别是 10.0.1, 10.0.2, 10.0.3）。Service wshoto-customer 给一个稳定 ClusterIP 10.0.100，DNS 名 wshoto-customer.wshoto.svc.cluster.local。其他 Pod 调这个名字，自动负载均衡到 3 个实例之一。这和第8章 Nacos 注册中心解决同一个问题——K8s Service 走集群内 DNS，Nacos 走服务名注册发现。

原文 4.6

概念4：Namespace（虚拟集群）

原文术语：Kubernetes 中的虚拟集群，用于在同一物理集群中划分多个虚拟环境

人话解释：一个物理 K8s 集群切多个 Namespace，资源（Pod/Service/ConfigMap）属于某个 Namespace。公司用它做环境隔离：生产业务在 wshoto、灰度在 wshoto-gray、中间件在 wshoto-middleware。Namespace 之间默认隔离，但可以跨 namespace 调用（用全名 namespace.svc）。

与其他概念的关系：Namespace 是资源边界；框架的 lane 泳道（第8章）是流量路由边界。公司用 Namespace + laneId 双重隔离：wshoto 命名空间的 Pod 打 MASTER 标，wshoto-gray 的 Pod 打 GRAY 标。

原文 4.2 + 6.2

概念5：Ingress（七层负载均衡）

原文术语：Kubernetes 的七层负载均衡器，提供基于域名和路径的 HTTP/HTTPS 路由

人话解释：Service 的 ClusterIP 只能在集群内访问，NodePort/LoadBalancer 暴露 TCP 端口。但生产对外通常是「按域名+路径」分流：a.wshoto.com 走服务 A，b.wshoto.com/api 走服务 B。Ingress 就是干这个的，公司用 traefik 作为 Ingress 控制器。

三大作用：①域名虚拟主机 ②路径路由 ③TLS/HTTPS。

原文 4.7

概念6：ConfigMap vs Secret

原文术语：ConfigMap（非敏感配置）/ Secret（敏感信息，Base64 编码）

人话解释：把配置和镜像解耦。ConfigMap 存普通配置（日志级别、特性开关）；Secret 存密码、Token、证书（Base64 编码，不是加密，但和 ConfigMap 分开管理）。两者都能用「环境变量」或「文件挂载」注入 Pod。

呼应第8章：框架用 Nacos 做配置中心，业务配置大多在 Nacos；但 K8s 层面的 Secret（如镜像拉取凭证 kubernetes.io/dockerconfigjson、TLS 证书）仍用 K8s Secret 管理。
类型用途示例
Opaque通用密钥数据库密码、API 密钥
dockerconfigjson镜像拉取密钥私有镜像仓库认证
tlsTLS 证书HTTPS 证书

09 误解与边界

误解1：「Pod 挂了自己会重启」

为什么容易误解：Docker 容器有 restart policy。

原文真正说了什么：Pod 是临时对象，控制器（Deployment）才是负责保证期望状态的对象。Pod 本身不会「自我修复」，是控制器发现副本数少了再创建新的。

如何避免：排查 Pod 故障时要看 Deployment 状态、副本数、事件，不只看单个 Pod。

误解2：「Service 就是负载均衡器」

为什么容易误解：Service 有负载均衡能力。

原文真正说了什么：Service 的核心是服务发现 + 稳定访问入口。它给一组 Pod 一个稳定的 ClusterIP + DNS 名，并负载均衡到后端 Pod。负载均衡是手段，稳定入口才是目的。

如何避免：理解 Service 解决的是「Pod IP 临时性」问题，不只是「分发流量」。

误解3：「命名空间 = 完全隔离」

为什么容易误解：Namespace 听起来像防火墙。

原文真正说了什么：Namespace 是资源边界（Pod/Service/ConfigMap 属于某 Namespace），不是网络隔离。默认情况下 Namespace 之间网络是通的，只是资源对象分开管理。

如何避免：真正做网络隔离要用 NetworkPolicy；做流量路由隔离用 lane 泳道（第8章）+ 命名空间组合。

误解4：「Secret 是加密的」

为什么容易误解：叫「Secret」听起来像加密。

原文真正说了什么：Secret 数据是Base64 编码，不是加密。Base64 是编码格式，任何人都能解码。它的安全性来自访问控制（RBAC）和分发机制，不是编码本身。

如何避免：敏感数据仍要走 KMS 或第7章 8.7 的密钥管理（环境变量/Secret 注入，不进仓库）。

误解5：「K8s Service 能替代 Nacos」

为什么容易误解：两者都做服务发现。

原文真正说了什么：K8s Service + DNS 只在集群内做服务发现；公司业务用 Nacos（discovery-nacos-boot-starter）是因为它支持多环境灰度路由（lane 泳道）——按租户把流量导到 MASTER/GRAY，K8s Service 做不到这种业务级路由。

如何避免：基础设施发现用 K8s Service；业务级灰度路由用 Nacos + lane。
