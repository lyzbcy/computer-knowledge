01 学习目标与阅读路径

这是一份写给"会写前端代码、但第一次想搞清楚线上偶发问题怎么排查"的同学的拆解地图。它要讲清一件事：用户在生产环境点了哪几下、发了什么请求、出了什么错——你怎么把它"重演"出来。读完这一章，你能做到下面五件事。

1
理解前端日志的用途：它自动记录用户操作（路由跳转含参数、网络请求出入参），加上开发者自定义日志，专门用来定位偶发问题；小程序未引入。
2
掌握 tag + message 的正确写法：tag=业务场景（如 GroupSend-TODO）多页面共用，不要拼接子过程；message 传文本不传 JSON 对象（避免循环引用），Error 类型传 error.message。
3
会用 CLS 检索日志：知道子账号、日志集/主题名、project 枚举（qv-admin/qv-admin-h5）、Lucence 语法、数据在 msg 字段、用 trace_id 查后端日志。
4
会获取 deviceId：PC 端在浏览器输 javascript:alert(localStorage.__ws_device_id) 或看控制台；移动端企微管家搜"##设备码##"或远程连企微 PC 端。
5
知道 Sentry 是什么：项目中未捕获的异常会上报 Sentry（wshoto.sentry.io，找老田开通），详情含 deviceId，可和 CLS 联动。
阅读路径（按顺序）

先在 02 补 6 个零件 → 在 03/04 看清"这份文档在解决什么、整体怎么搭" → 在 05/06 抓住 5 条核心判断和 5 个关键概念 → 在 07 自己提问 → 在 08 闯 8 道闭环题 → 在 09/10 看边界 → 在 11 出报告。

02

零基础背景包

在拆原文前，先装 6 个最基本的零件。每个都标了"背景补充"——它帮你读懂原文，但不是日志系统自己的设计论点，而是帮你建立"前端线上问题怎么追踪"的常识。

背景补充 1 · 日志埋点（log / track）

在代码里特定位置调用一个"上报"函数，把当时的上下文（用户点了啥、参数是什么、出了什么错）写进日志系统。分两类：自动埋点（框架帮你记，不用你写）和手动埋点（你自己调函数记）。

类比 C：埋点 ≈ 在关键函数里 printf 调试信息，只不过这些信息会被发到服务器存起来，事后能搜。
为什么现在需要知道：前端日志的"自动收集（路由/请求）"和"手动调用（this.$log）"就是这两类。
背景补充 2 · XHR 代理（拦截 XMLHttpRequest）

浏览器发网络请求靠 XMLHttpRequest（XHR）或 fetch。日志系统在全局"换掉"原生的 XHR 对象，包一层自己的逻辑——这样每次发请求都会先经过它，它就能悄悄把请求参数和返回内容记下来。

类比 C：XHR 代理 ≈ 你重写了 libc 的 send() 函数，先 printf 一份再调真的 send()。
为什么现在需要知道：原文的 ajaxError.ts 就是干这件事的，理解了"代理"才懂为什么 AJAX 请求会被自动记录。
背景补充 3 · localStorage（浏览器本地存储）

浏览器提供给每个网站的一块持久化存储空间，关浏览器也不会丢。前端用 localStorage.setItem(key, value) 存，getItem(key) 取。微盛的 deviceId 就存在 localStorage.__ws_device_id。

类比 C：localStorage ≈ 一个持久化的 key-value 配置文件，程序读写它，关机不丢。
为什么现在需要知道：获取 deviceId 就是从 localStorage 里读这个 key；日志暂存也靠它。
背景补充 4 · sendBeacon（页面卸载时上报）

浏览器的一个 API，专门用来在"页面马上要关闭/跳走"的瞬间发数据，发完再关。普通请求在页面关闭那一刻会被取消，sendBeacon 不会。这是日志上报的第一选择。

类比 C：sendBeacon ≈ 进程退出前用 atexit 注册一个"把日志 flush 到磁盘"的钩子，保证最后那批数据不丢。
为什么现在需要知道：原文说上报按 sendBeacon → fetch → xhr 降级，sendBeacon 排第一就是为了应对"用户突然关浏览器"。
背景补充 5 · Lucence 检索语法

Elasticsearch/腾讯云 CLS 用的查询语言。核心：key:value 表示"在某字段里查某值"；AND OR NOT () 组合逻辑；"" 精确短语；* ? 通配；[A TO B] 范围。注意大小写敏感：AND 是运算符，and 是普通文本。

类比 C：Lucence ≈ 一套比 grep 更强的"带字段名的正则"，能指定"只在 msg 这个字段里搜"。
为什么现在需要知道：CLS 检索全靠这套语法，写错大小写就搜不到。
背景补充 6 · Sentry（错误监控平台）

一个第三方服务，前端代码里接它的 SDK 后，所有"未被 try-catch 捕获的异常"会自动上报到 Sentry 服务器。你能在 Sentry 网站上看到错误栈、出错时的设备信息、用户信息，还能看同一个错误发生过多少次。

类比 C：Sentry ≈ 一个帮你自动收集 core dump + 运行环境的线上服务，比你手动加 printf 高级。
为什么现在需要知道：微盛的 Sentry 在 wshoto.sentry.io，和 CLS 是两套互补的系统。

自动记录用户操作流程中的关键信息，支持开发者添加自定义日志，帮助开发者定位偶发问题。

04

原文结构地图

判断结构类型：机制流程 + 工具速查（先讲机制怎么转，再讲怎么用工具看数据）。整篇是一条"日志从产生→上报→存储→检索→联动"的链路，最后 Sentry 是补充。不要把它读成并列清单。

主线：一条日志的完整生命周期 （机制流程）
  ├─ 1. 日志怎么产生（两类）
  │    自动收集：AJAX 请求（XHR 代理，ajaxError.ts）+ 页面跳转（路由守卫埋点）
  │    手动调用：开发者 this.$log({ tag, message, level })
  ├─ 2. 怎么上报（时机 + 方式）
  │    时机：默认延迟 3S；易出错场景（如移动端待办）配立即上报；3S 内关浏览器存 localStorage 下次开上报
  │    方式：sendBeacon → fetch → xhr 降级；内容 AES 加密
  │    边界：和 SAAS 标品分开部署的项目（私有化/企点/有群）不用日志库
  ├─ 3. 怎么定位用户（deviceId）
  │    PC：javascript:alert(localStorage.__ws_device_id) 或控制台看 __ws_device_id
  │    移动端：企微管家搜"##设备码##"或远程连企微 PC 端
  ├─ 4. 怎么看数据（CLS 检索）
  │    腾讯云 CLS：上海，日志集 TKE-TEST/TKE-PROD，主题 tke-*-service-logtopic
  │    子账号：wshoto-log / Jswshoto@2021
  │    数据在 msg 字段；project=qv-admin(PC)/qv-admin-h5(H5)；trace_id 查后端
  └─ 5. 检索语法（Lucence）
      AND/OR/NOT/()/:/""/*/?/>/<=/TO/[]/_exists_；大小写敏感；默认 5 分钟需调大
补充：Sentry（未捕获异常上报） （主题簇，和 CLS 互补）
  ├─ 项目未捕获异常自动上报 wshoto.sentry.io（找老田开通）
  ├─ 支持 PC 端和移动端
  └─ 详情含 deviceId，可和 CLS 联动查询
节点关系说明

主线四步是顺序链条（产生→上报→定位用户→检索）；CLS 和 Sentry 是互补关系（CLS 记用户行为、Sentry 记未捕获异常，靠 deviceId 联动）；"私有化不用日志库"是边界条件，独立于主链路但必须记住。把这三层分开看，就不会被一堆名词绕晕。

05

核心判断与依据

挑出 5 条最硬的判断。每条都附原文依据和类型标签。

判断 1 · 前端日志的核心价值是"复现用户操作"，不是单纯记错误

自动记录的是路由跳转（含参数）+ 网络请求出入参，这两类信息加上开发者自定义日志，能让你把"用户那一刻点到了哪、传了什么、接口返了什么"完整重演。它定位的是偶发问题，不是常规报错。判断

自动记录用户操作流程中的关键信息……路由跳转（包含参数）、网络请求出入参……帮助开发者定位偶发问题。

为什么重要：理解了这条，你就懂为什么要记"请求入参"——因为复现问题靠的是"按用户传的参数重放"。

判断 2 · tag 定义"业务场景"且多页面共用，子过程放 message 不要拼进 tag

tag 是业务场景的标识（如群发待办 = GroupSend-TODO），多个页面共用同一个 tag。一个业务里的子过程（如 step1/step2）不要写成 GroupSend-TODO-Step1，而应该把 step1 写进 message。否则 tag 越拆越碎、检索时根本对不齐。事实

tag 代表业务场景，如群发待办可定义为 GroupSend-TODO；多个页面可使用相同的 tag；一个业务过程中的子过程不要采用拼接 tag 的方式，而应该在 message 中添加。

易误读：tag 不是"越细越好"，而是"同一业务场景共用一个"。粒度卡在"业务场景"，不卡在"每一步操作"。

判断 3 · message 传文本不传 JSON 对象；Error 类型传 error.message

如果要把 JSON 塞进 message，必须先转成字符串，且避免循环引用导致 JSON.stringify 失败——一旦失败，后续上报流程直接卡死。Error 对象不能整个传，要传 error.message。事实

message 需传文本值，如果需要对 JSON 进行转化，需避免 JSON 中有循环引用导致调用 JSON.stringify 失败引起后续流程无法执行……如果 message 属于 Error 类型，需自行传 error.message 字段，不要直接传 error。
判断 4 · 默认延迟 3S 上报，但易出错场景要配立即上报

默认不是立即上报，而是攒 3 秒再发（批量、省请求）。代价是：3 秒内用户关了浏览器，这批数据就丢了——所以这种情况会暂存 localStorage 下次开再发。但对于"用户可能随时关浏览器又容易出错"的场景（移动端待办），必须配置立即上报。推论

日志上传默认非为立即上报方式，延迟 3S 上报，如果在 3S 内用户关闭浏览器，则日志暂存 localStorage……对于易出问题且用户可能随时关闭浏览器的场景，如移动端待办场景，需配置立即上报。

易误读：默认 3S 不是"忘了配立即上报也没关系"——关键业务路径必须显式配立即上报，否则丢日志。

判断 5 · 和 SAAS 标品分开部署的项目（私有化/企点/有群）不用日志库

日志库只服务于 SAAS 标品。私有化项目、企点、有群这些独立部署的项目，不应该引入日志库。事实

和 SAAS 标品分开部署的项目均不应该使用日志库，如私有化项目，企点，有群。
能用日志库：SAAS 标品
不能用日志库：私有化项目 / 企点 / 有群
06

关键概念拆解

5 个概念，环环相扣：自动日志（路由/请求）+ 自定义日志（tag/message/level）产生数据 → deviceId 标识是哪个用户 → CLS 检索把数据捞出来 → Sentry 补未捕获异常。

① 自动日志（路由 + 请求）
定义框架自动记录的两类信息：页面跳转（含参数）+ 网络请求的入参/出参。开发者不用写代码。
机制AJAX 请求通过代理 XHR 实现，代码在 src/plugins/monitor/error/modules/ajaxError.ts；页面跳转不是用 history.pushState 拦截，而是直接在路由守卫里加埋点。
类比 C：代理 XHR ≈ 你重写了系统的 send()，先 printf 一份请求/响应再调真的 send()；路由守卫埋点 ≈ 在 main() 的每次 switch-case 前打一行日志。
关系自动日志负责"用户操作回放"；自定义日志负责"开发者主动想记的事"。两者都进 CLS。
AJAX 请求通过代理 XHR 实现……页面跳转未通过拦截 history.pushState 实现，而是直接在路由守卫中添加的埋点。
不要误解成"正确请求的返回内容也会被完整记录"——正确请求只记请求参数，失败请求才记返回内容。想看正确请求的返回，要用 trace_id 查后端。
② 自定义日志（tag / message / level）
定义开发者手动调用 this.$log({ tag, message, level }) 上报的日志，用来补充自动日志记不到的业务上下文。
tag业务场景标识（如 GroupSend-TODO），多页面共用；子过程不拼进 tag，放 message。
message详情；传文本不传 JSON 对象（避免循环引用导致 JSON.stringify 崩）；Error 传 error.message。
level异常传 'Error'（网络异常/jsapi 异常/异常分支）；其它传 'Info' 或不传。
this.$log({ tag:'GroupSend-TODO', message:'提交群发，目标数=120', level:'Info' })
异常信息需传 'Error'……其它场景均传 'Info' 或不传。
不要误解成数据格式只支持 string 和 {key: value}，不是什么都能塞；别把整个对象/数组当 message。
③ deviceId（用户设备标识）
定义每个用户设备在前端的唯一标识，存在 localStorage.__ws_device_id。它是把"某条日志"和"某个报障用户"对应起来的钥匙。
PC 端获取方式一（推荐）：让用户在登录后台的浏览器地址栏输 javascript:alert(localStorage.__ws_device_id) 回车弹框；方式二：让用户打开控制台，在 localStorage 里找 __ws_device_id。
移动端获取方式一：客户打开移动端"企微管家"，找 WsSearch 控件（如 TAB 搜索框），输 ##设备码##（# 为英文符号）回车查看；方式二：远程连接客户的企业微信 PC 端，再按 PC 端方式查 localStorage。
类比 C：deviceId ≈ 程序给每台机器生成的 hostId，日志带上它就能筛出"只看这台机器的日志"。
关系CLS 检索、Sentry 详情都靠 deviceId 关联到具体用户。
不要误解成" deviceId 是用户账号"——它是设备标识，同一账号换设备会变；同一设备清了 localStorage 也会重新生成。
④ CLS 检索（腾讯云日志服务）
定义腾讯云的日志检索平台，前端日志最终都存这里，通过网页搜索。前端视角的检索语法、project 枚举是前端特有的。
登录腾讯云子账号：用户名 wshoto-log / 密码 Jswshoto@2021（主帐号 ID 100014537081）。
日志集/主题区域=上海；测试环境：日志集 TKE-TEST / 主题 tke-test-service-logtopic；生产灰度：日志集 TKE-PROD / 主题 tke-prod-service-logtopic。
project 枚举qv-admin（PC 端）/ qv-admin-h5（H5 端）——用 app_name 联合搜索。
数据位置所有打点内容写入 msg 字段；查后端日志/返回结果用 trace_id:"具体traceId"。
检索套路：app_name:qv-admin AND msg:"群发"
查后端：trace_id:"abc123def456"
所有的数据都是写入到 msg 字段下，利用项目名称（app_name）与 msg 联合搜索……可通过搜索 trace_id:"具体的traceId" 查看后端日志/返回结果。
不要误解成CLS 默认只搜最近 5 分钟，时间范围在搜索框右侧，通常要手动调大，否则什么都搜不到。
⑤ Sentry（未捕获异常监控）
定义第三方错误监控平台。项目中所有未被 try-catch 捕获的异常会自动上报到 Sentry，辅助定位问题。
入口https://wshoto.sentry.io/（需找老田开通权限）；登录后按项目分类，目前支持 PC 端和移动端。
详情点开错误能看到问题描述 + 错误栈；附加信息里包含当前用户的 deviceId，可以拿这个 deviceId 去 CLS 联动查用户行为。
类比 C：Sentry ≈ 一个自动收集线上 core dump 的服务，还顺带记了崩溃机器的 hostId（deviceId）。
关系Sentry 和 CLS 互补：Sentry 管"程序崩了"，CLS 管"用户干了啥"；靠 deviceId 把两者串起来。
项目中未捕获的异常会上报到 Sentry 平台……详情的附加信息中还包含当前用户的设备号，可以腾讯云 CLS 联动查询。
不要误解成Sentry ≠ CLS。Sentry 只收"未捕获异常"，不收路由/请求/自定义日志；CLS 才是行为日志的主战场。
07

苏格拉底式阅读关卡

不直接给答案，自己想。参考答案在每题下方，但请先停 30 秒再展开。

Q1 · 入门为什么要"延迟 3S 上报"而不是每条日志立即上报？
为了批量、省请求。用户操作会产生大量日志点，每条都立即发会拖慢前端、堵塞网络。攒 3 秒合并发，性能好得多。代价是 3 秒内关浏览器会丢——所以用 localStorage 兜底，下次打开补发。
提示：想想"实时发"和"攒一批发"各自的代价。
Q2 · 入门为什么 tag 不要拼接子过程（不要写 GroupSend-TODO-Step1）？
因为 tag 的作用是标识业务场景、便于跨页面检索。如果每个子过程一个 tag，tag 会越拆越碎，同一个业务被切成 N 个 tag，检索时根本对不齐。子过程应该写进 message，让 tag 保持"一个业务场景一个名"的粒度。
Q3 · 进阶为什么私有化项目、企点、有群不能用日志库？
因为日志库是和 SAAS 标品绑定的一套基础设施（CLS、加密、上报通道都按 SAAS 标品的部署搭的）。私有化/企点/有群是分开部署的独立项目，没有这套后端支撑，强行引入日志库要么上报失败、要么数据进了不该进的地方。所以这些项目一律不引入。
提示：注意"分开部署"这四个字——日志库不是孤立的库，它依赖一整套后端。
Q4 · 进阶message 为什么不能直接传 JSON 对象、也不能直接传 Error？
传 JSON 对象：内部会对它 JSON.stringify，如果对象有循环引用（如 a.b = a），stringify 直接抛错，导致后续上报流程卡死。传 Error：Error 对象不是纯数据，直接传会出问题，所以要传 error.message（文本）。本质都是"只传可序列化的文本"。
Q5 · 进阶正确的网络请求只记请求参数、不记返回内容，为什么？想看返回内容怎么办？
为了控制日志量、避免服务器压力。成功请求的返回内容往往很大，全记会撑爆存储和带宽，所以只记入参。失败请求才记返回内容（便于排错）。想看成功请求的返回，要拿到那次请求的 trace_id，去 CLS 搜 trace_id:"xxx" 查后端日志/返回结果。
Q6 · 深度Sentry 报了一个错，怎么定位到是哪个用户、他当时做了什么？
分两步：① 在 Sentry 错误详情的附加信息里找到 deviceId；② 拿这个 deviceId 去腾讯云 CLS 检索（用 app_name 联合 + deviceId），看这个用户在出错前后的路由跳转、网络请求、自定义日志——也就是把"用户操作回放"拼出来。这就是 Sentry 和 CLS 联动的标准套路。
提示：deviceId 是连接 Sentry 和 CLS 的那把钥匙。
Q7 · 深度用户报障说"刚操作就出问题了"，但你去 CLS 搜却什么都没有，最可能的原因是什么？
最可能是时间范围没调大。CLS 默认只搜最近 5 分钟，用户报障时往往已经过了几分钟甚至更久，默认范围根本覆盖不到。另外也要确认搜的是不是对应环境的日志集/主题（TKE-TEST 还是 TKE-PROD），以及 project（qv-admin / qv-admin-h5）有没有加。

误解与边界

误解 1 · "message 可以随便传 JSON 对象/直接传 error"
为什么容易误解看 message 能"记详情"，就以为啥对象都能塞。
原文真正说了message 只支持 string 和 {key: value}；JSON 要避免循环引用导致 JSON.stringify 失败、卡死后续流程；Error 要传 error.message，不能直接传 error。
原文没有说"message 是个对象容器"——它只收可序列化的文本/简单键值。
如何避免传对象前先想"它能不能 JSON.stringify"；Error 永远传 error.message。
误解 2 · "CLS 打开就能搜到全部历史日志"
为什么容易误解搜索引擎用惯了，以为默认就是全量。
原文真正说了搜索框右侧时间范围默认 5 分钟，通常需要调大。
原文没有说"默认搜全部"——5 分钟外的数据默认搜不到。
如何避免每次搜之前先确认时间范围，按报障时间往前往后调够。
误解 3 · "私有化/企点/有群项目也能用前端日志库"
为什么容易误解以为日志库是个通用 npm 包，哪个项目都能装。
原文真正说了和 SAAS 标品分开部署的项目（私有化、企点、有群）均不应该使用日志库。
原文没有说"日志库全项目通用"——它绑定 SAAS 标品的那套后端基础设施。
如何避免接手新项目先问清楚是不是 SAAS 标品；不是，就别引日志库。
误解 4 · "tag 越细越好，每一步操作一个 tag"
为什么容易误解觉得"分得越细越容易定位"。
原文真正说了tag 代表业务场景，多个页面共用同一个 tag；子过程不要拼进 tag，要写进 message。
原文没有说"tag 要细分到每一步"——粒度卡在"业务场景"，不是"每步操作"。
如何避免tag 按"业务场景"命名（如 GroupSend-TODO），步骤信息一律进 message。
误解 5 · "正确的网络请求也会完整记录返回内容"
为什么容易误解以为自动日志会把所有出入参都完整记下来。
原文真正说了正确的网络请求结果仅记录请求参数，失败的网络请求才会记录返回内容。想看正确请求的返回，要靠 trace_id 查后端日志。
如何避免要查成功接口的返回内容，记下 trace_id 去后端日志捞，别指望 CLS 里有。

背景知识缺口

要彻底吃透这一章，建议补这 4 个背景。现在不补也行，遇到不懂的再回头看。

缺口 1 · XHR 代理 / fetch 拦截的原理

原文说"AJAX 请求通过代理 XHR 实现"，但没讲怎么代理。建议补：怎么重写 window.XMLHttpRequest、怎么在 open/send 里插钩子、fetch 怎么 monkey patch。类比 C：≈ 在头文件里把系统 send 重定义成你的 wrapper，先记日志再调真 send。为什么重要：懂了代理，才懂"为什么所有请求会被自动记录、为什么能在 ajaxError.ts 一个文件里统一处理"。

缺口 2 · sendBeacon / fetch / xhr 三种上报的取舍

原文说"按 sendBeacon → fetch → xhr 顺序降级"，但没讲为什么。建议补：sendBeacon 为啥适合页面卸载时发、它的大小限制、fetch 的 keepalive 标志、为什么 xhr 是兜底。下一步追问：既然 sendBeacon 最好，为什么不只用它？答：它有数据大小限制、请求方法/头部受限。

缺口 3 · AES 加密与日志安全

原文说"内容采用 AES 加密"，但没讲细节。建议补：对称加密基本原理、前端加密后端怎么解、密钥怎么管理、为什么要加密（防止中间人看到用户操作数据）。为什么重要：理解了加密，才知道为什么日志内容在 CLS 里看到的是结构化数据而不是明文报文。

缺口 4 · Lucence 全文检索与 CLS 数据结构

建议补：倒排索引原理、分词器、为什么有 msg 这样的字段、key:value 检索和全文检索的区别、为什么大小写敏感。为什么重要：理解了"字段"概念，才知道为什么要写 app_name:qv-admin AND msg:"群发" 而不是裸搜"群发"。

可以暂时不补的

路由守卫的具体实现（Vue Router beforeEach）、AES 加密的具体密钥与算法实现、企业微信 PC 端控制台打开的详细步骤——这些是操作层细节，不影响理解日志系统的整体骨架。

📝 Lucence 检索语法速查（原文易踩坑点）

CLS 用 Lucence 语法，大小写敏感（AND 是运算符，and 是普通文本）。下面是最常用的几条：

语法说明示例
:键值检索（在某字段里查）level:ERROR
AND与（注意大写）level:ERROR AND pid:1234
OR或（注意大写）level:ERROR OR level:WARNING
NOT非（注意大写）level:ERROR NOT pid:1234
()分组，控制优先级(ERROR OR WARNING) AND pid:1234
""精确短语（顺序不变）name:"john Smith"
* / ?通配（多字符/单字符，不支持前缀模糊）host:www.test*.com
> >= < <=范围比较status:>=400
TO / []范围（含边界）age:[20 TO 30]
_exists_字段是否存在_exists_:userAgent
为什么现在需要知道：新手常写出 and/or（小写）搜不到东西，或者忘记指定字段（msg:）裸搜——记住"运算符大写 + key:value"这两条，能省很多来回。
