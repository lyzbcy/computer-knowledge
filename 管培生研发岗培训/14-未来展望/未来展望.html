未来展望

大数据下一步不是更大，而是更可信、更自动、更能支撑 AI 和业务动作。从报表底座走向智能中枢。本章你将学会：未来能力地图四层、AI Native 受控开发六步、影响分析式运维治理；📖 新版增补：三类 AI 应用——DB Agent 智能问数（重点：六步流程、语义层、五种实现思路、上线前六项控制）、预测分析与实时智能决策、个性化推荐与决策优化。

02

零基础背景包

背景补充 影响分析（Impact Analysis）

变更（删表、改字段、调口径）发生前，先查清「谁会被波及」：下游哪些表、报表、任务依赖它。查完再动手。

为什么现在需要知道：本章主张运维治理从「事后救火」转向影响分析。

背景补充 AI Native

以 AI 为第一生产力来组织开发流程：人提需求，AI 产出设计和代码，人负责审查与把关。

为什么现在需要知道：本章讲 AI Native 开发为什么必须「受控」。它不是本文的主张本身，只是帮助你读懂原文。

背景补充 DDL / DAG（承接第13章）

DDL 是建表语句（看字段、注释、类型）；DAG 是任务依赖图。AI 探查候选表时看的就是 DDL、已有 SQL、调度和样例数据。

为什么现在需要知道：理解受控开发第二步「探查候选表」在看什么。

背景补充 数据治理

对数据资产做管理：口径统一、权限脱敏、生命周期、质量监控。目的是让数据「敢被相信、敢被复用」。

为什么现在需要知道：治理层是未来能力地图四层之一。

背景补充 📖 DB Agent（智能问数）

业务人员用自然语言提问，系统自动选择查询路线（语义层/查询 API/SQL 模板/Text-to-SQL）、校验权限、执行查询并返回数字+表格+SQL+指标口径的产品形态。参考：Microsoft Fabric Data Agent。

为什么现在需要知道：新版自学手册把 DB Agent 列为三类 AI 应用的重点方向。

背景补充 📖 Text-to-SQL 与语义层

Text-to-SQL：把自然语言直接转成 SQL，覆盖面广但依赖模型和元数据质量。语义层：把「新增用户」「活跃客户」等业务说法映射成统一指标算法、维度、字段和权限的「可执行业务词典」。

为什么现在需要知道：DB Agent 的核心选型问题是「什么问题走语义层、什么问题走 Text-to-SQL」。

05

核心判断与依据

判断1：未来的问题不是规模，是可信和复用

核心判断：只做多表、多任务、多报表，团队会越来越忙，结果越来越难解释；真正要解决的是数据能否稳定复用、自动发现问题、支撑 AI，并让内部和用户都敢相信。

原文依据（第2页）：「如果只是多表、多任务、多报表，团队会越来越忙，但结果越来越难解释。」「真正要解决的问题：数据能否稳定复用、自动发现问题、支撑 AI，并让内部和用户都敢相信。」

判断 为什么重要：给「下一步投入」定方向。误读：以为未来展望=新技术清单。

判断2：报表只是出口之一，大数据要成为智能中枢

核心判断：数据还要连接 AI、运营动作和用户洞察；能力地图分数据底座、治理层、智能层、行动层。

原文依据（第3页）：「报表仍然重要，但它只是出口之一。数据还要连接 AI、运营动作和用户洞察。」「未来能力地图：数据底座、治理层、智能层、行动层。」

判断 为什么重要：重新定位数据团队的价值出口。误读：报表不再重要。

判断3：AI Native 开发的难点是「知道什么时候不该写」

核心判断：AI 写 SQL 不难，难的是知道这条 SQL 什么时候不该写；因此要六步受控，生产发布必须人工审批、不由 AI 绕过边界。

原文依据（第4页）：「AI 写 SQL 不难，难的是知道这条 SQL 什么时候不该写。」「人工审批——生产发布进入受保护系统，不由 AI 绕过边界。」

判断 为什么重要：划清 AI 权限红线。误读：AI 提效=放开生产权限。

判断4：运维和治理要从事后处理变成影响分析

核心判断：任务失败、数据删除、字段变更、口径调整，都应该先知道影响范围；告警要更准——不是发更多群消息，而是带影响范围、原因线索和建议动作。

原文依据（第5页标题+「告警要更准」节）。

判断 为什么重要：定义了告警质量标准。误读：告警越多越负责。

判断5：会话删除不能只删 DWD 原始消息

核心判断：删除治理必须覆盖上层——DWS、ADS 和报表也要同步处理或重算。

原文依据（第5页）：「会存删除治理——不能只删 DWD 原始消息，上层 DWS、ADS 和报表也要同步处理或重算。」

事实 为什么重要：分层（第12章）与删除合规的连接点。误读：删了源头就干净了。

判断6：智能分析必须带证据链，越流畅越要警惕

核心判断：没有证据链的 AI 结论，越流畅越容易让人放松警惕；证据链包括指标引用、原文证据、模型批次、质量校验、运行记录、复核入口。

原文依据（第6页）：「没有证据链的 AI 结论，越流畅越容易让人放松警惕。」

判断 为什么重要：AI 分析的信任底线。误读：流畅=可靠。

📖 判断7：DB Agent 信息不全时先追问，不能自行猜测口径

核心判断：如果时间范围、统计对象或指标含义不清楚，系统应先追问；一次查询应返回数字、表格、SQL 和指标口径（业务人员看结果，数据人员可检查 SQL 和口径）。

自学手册依据（第8页）：「如果时间范围、统计对象或指标含义不清楚，系统应先追问，不能自行猜测口径。」

判断 这是旧版「口径先行」在问数场景的落地。误读：让 Agent 自己挑一个口径跑出数来「先看看」。

📖 判断8：生产系统不把所有问题都直接交给模型生成 SQL，混合路由被推荐

核心判断：语义层稳但覆盖窄、查询 API 最安全但受限、模板可控但数量膨胀、Text-to-SQL 覆盖长尾但风险高；混合路由按问题类型分流（固定指标走语义层，高风险走 API，半固定走模板，长尾走 Text-to-SQL），兼顾稳定性和覆盖范围。

自学手册依据（第10页）：「混合路由（推荐）：先判断问题类型……适合真实生产系统；需要维护路由规则和统一审计。」

判断 为什么重要：这是 DB Agent 综合设计题的标准答案框架。误读：All-in Text-to-SQL 图省事。

📖 判断9：上线前六项控制要一起生效，只限制返回行数不够

核心判断：指标定义、表白名单、只读账号、租户和用户权限、超时控制、审计日志六项一起生效；只限制返回行数不能解决指标算错、越权查询和写入数据等问题。

自学手册依据（第11页）：「上线前六项控制要一起生效」「只限制返回行数不能解决指标算错、越权查询和写入数据等问题。」

判断 为什么重要：DB Agent 的安全底线。误读：加个 limit 就算安全上线。

📖 判断10：预测离线训练实时使用，推荐要反馈闭环

核心判断：预测模型用历史数据离线训练，Kafka/Flink 流式链路实时调用；结果至少保留预测分数、判断阈值、模型版本和触发动作。推荐系统输出排序列表+分数+理由+建议动作，点击、购买、忽略、拒绝和投诉等反馈要重新进入数据平台，用于调整特征、规则和模型。

自学手册依据（第11-12页）：「离线训练，实时使用」「推荐结果还要持续校正」。

判断 为什么重要：两类应用的价值都在「持续校正」。误读：模型上线即一劳永逸。

06

关键概念拆解

智能中枢

作者用法：大数据的下一个形态，报表只是出口之一，还连接 AI、运营动作和用户洞察。人话：数据从「出报表的后厨」变成「驱动动作的大脑」。

数据底座（存算）→ 治理层（可信）→ 智能层（分析）→ 行动层（业务动作） 原文依据（第3页）：「未来能力地图：数据底座、治理层、智能层、行动层。」

不要误解成：一个单一的新产品或系统名。

AI Native 受控开发（六步）

作者用法：识别需求（拆实体/指标/粒度/窗口）→ 探查候选表（字段/注释/DDL/已有SQL/调度/样例）→ 生成设计（血缘/DAG/幂等/校验）→ test preview → 独立 Review → 人工审批。

原文依据（第4页六节编号 01-06）。

不要误解成：六步都由 AI 自动走完——Review 和审批是人的关卡。

影响分析

作者用法：变更前先知道影响范围（哪些任务失败会影响客户、字段变更波及谁、是否需要重算）。人话：动手前先看波及面。

原文依据（第5页标题与「真正要解决的问题」相关条目：哪个任务失败会影响客户，要能提前判断）。

不要误解成：出事后的复盘报告——它是「事前」动作。

更准的告警

作者用法：带影响范围、原因线索和建议动作，而不是把群消息发得更多。人话：一条告警=「谁受影响+可能为什么+建议怎么办」。

原文依据（第5页「告警要更准」节）。

不要误解成：告警数量指标。

会话删除治理

作者用法：删除请求要沿分层向上传导——DWS、ADS 和报表同步处理或重算。人话：删数据要删干净整条血缘，不然汇总里还残留。

原文依据（第5页「会存删除治理」节）。

类比（仅辅助理解）：像撤回一颗铆钉，要检查整架飞机哪些部位用了它。它帮助理解：变更沿依赖传播；它不能代表：技术上逐表手工删。

智能分析证据链（六要素）

作者用法：指标引用、原文证据、模型批次、质量校验、运行记录、复核入口。

原文依据（第6页六节并列）。

与第12章证据链六要素对照：结构一致、措辞略有差异（运行记录 vs 血缘链路），核心都是「能回查」。不要误解成：给 AI 结论盖一个「已审核」章就算证据链。

📖 DB Agent 完成一次问数的六步

①理解问题：拆出时间范围、统计对象、指标、维度和排序要求，信息不全时先追问；②选择实现路径：语义层/查询 API/SQL 模板/Text-to-SQL；③形成查询计划：指标、维度、过滤条件、关联路径、时间粒度和结果格式；④校验权限与风险：租户、用户、表白名单、敏感字段、查询成本和超时限制；⑤执行并校验：只读账号查 Doris，检查空结果、异常值、重复行和统计范围；⑥返回并留痕：数字/表格/SQL/指标口径+问题、查询计划、结果和审计日志。

理解问题 → 选路径 → 查询计划 → 权限风险 → 只读执行校验 → 返回留痕 自学手册依据（第8页）六节编号。

不要误解成：六步里任何一步可以让模型「自由发挥」——路径受控、账号只读、全程留痕。

📖 语义层：一份可以被系统执行的业务词典

六个方面：业务术语与别名（新增用户/新增客户/拉新人数是否同一件事）、指标定义（公式、去重键、粒度、适用范围）、时间规则（自然周/滚动 7 天/数据日期 vs 业务发生时间）、维度与关联（部门区域员工商品怎么分组、表怎么 Join）、物理映射（哪张表哪个字段、默认过滤条件）、权限与版本（谁能看哪个租户、指标变更从哪天生效）。

自学手册依据（第9页）六节并列。

两个「不是」：不是 DB Agent 的必经层；不是数仓新增的 DWS/ADS 层。它可以由指标平台、元数据服务、YAML/JSON 配置或查询 API 实现。

📖 DB Agent 五种实现思路对比

指标语义层：口径稳定、容易审计，适合经营指标和正式报表，前期要整理指标资产。查询 API/Tool：最安全最稳定，适合高频高风险场景，受接口范围限制。参数化 SQL 模板：建设成本低、结果可控，适合半固定分析，复杂问题要加模板。Schema 检索+Text-to-SQL：覆盖长尾问题，依赖模型和元数据质量，必须加权限、成本和结果校验。混合路由（推荐）：按问题类型分流，兼顾稳定性和覆盖范围，需维护路由规则和统一审计。

自学手册依据（第10页）五种做法对比表。

示例：「上周华南区域新增用户数」→ 指标=首次注册落在统计期内的去重用户数；时间=公司自然周转明确起止；维度=华南区域映射统一区域编码；数据与权限=查 DWS/ADS 表并自动追加租户和用户可见范围。

📖 预测分析与个性化推荐

预测分析：传统报表回答「已经发生了什么」，预测模型回答「接下来可能发生什么」——反诈风控（交易事件进流式任务，秒级告警拦截）、客户流失预测、业务量预测（提前安排人员和容量）。离线训练，实时使用；结果至少保留预测分数、判断阈值、模型版本和触发动作。

个性化推荐：按用户标签、历史行为、当前场景和业务约束对候选商品/内容/动作评分和排序——商品内容权益推荐、客户跟进顺序、服务方案/导购话术。输出推荐列表+分数+理由+建议动作；点击、购买、忽略、拒绝、投诉等反馈要回流数据平台，调整特征、规则和模型。

自学手册依据（第11-12页）方向 2、方向 3。

不要误解成：预测=报表加个趋势线；推荐=一次性排序——两者都依赖反馈持续校正。

误解与边界

误解1：「报表只是出口之一」= 报表不重要了

为什么容易误解：把递进读成否定。原文原话：「报表仍然重要，但它只是出口之一」。原文没说：要砍报表。避免方法：注意「仍然」这个限定词。

误解2：受控开发流程会拖慢 AI 提效

为什么容易误解：六步看起来繁琐。原文的立场是「AI 写 SQL 不难，难的是知道什么时候不该写」——受控是信任前提，不是阻力。避免方法：把 Review/审批当成可信的来源而不是成本。

误解3：AI 结论流畅、自洽，就可以直接信

为什么容易误解：流畅感本身就有说服力。原文明确警告：「没有证据链的 AI 结论，越流畅越容易让人放松警惕」。避免方法：看到 AI 结论先找六要素证据链。

误解4：影响分析是出事后的复盘

为什么容易误解：和「事后处理」混同。原文说变更「都应该先知道影响范围」——是事前动作。避免方法：变更单里先附影响面再审批。

复盘与学习报告

本章收束（原文第7页）

• 未来的大数据不是更大，而是更可信、更自动、更可复用。
• AI 分析、运营动作、客户洞察、自动巡检都会成为数据出口。
• 真正的目标是让数据说清楚自己是谁、从哪里来、为什么可信。
• 三讲合起来：为什么需要大数据、微盛怎么做、接下来往哪里走。

📖 新版自学手册收束（第三部分 + 学习小结）

• 三类 AI 应用分工：DB Agent 用于查数（输出数字/表格/SQL/口径），预测模型用于识别风险和趋势（输出预测分数/风险等级/触发动作），推荐系统用于选择合适的内容和动作（输出推荐列表/分数/理由/建议动作）——三类应用都依赖统一指标、数据质量、权限和运行记录。
• DB Agent 六步 + 五种实现思路（推荐混合路由）+ 上线前六项控制一起生效。
• 学习小结三条：技术演进由业务问题推动，不为技术名词盲目升级；数据开发先确认统计对象、时间范围、数据粒度和算法再动手；三类 AI 应用共用同一套平台基础。
