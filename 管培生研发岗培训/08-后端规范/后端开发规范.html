后端开发规范

基于《Wshoto 后端开发规范 v1.5》（2026-07-17）深度拆解 · 受众：Java 后端开发管培生

01 学习目标与阅读路径

这份规范是新增代码强制执行、存量代码逐步治理的内部硬约束。学完你应该能做到：

1
区分 MUST / MUST NOT / SHOULD 的约束等级——能判断一条规则违反后是「绝对禁止」还是「需充分评估」，能说出鉴权、租户隔离、注入防护属于红线。
2
背出技术基线——Java 17、Maven、Spring Boot、Spring Cloud、Nacos、OpenFeign、MyBatis/MyBatis-Plus、PostgreSQL、Redis、RocketMQ/Spring Cloud Stream。
3
说清分层职责——Controller 只做协议入口/参数校验/调用 Service；Repository 集中数据访问；每一层用本层对象（Request/DTO/Entity/DO/Response），相邻层显式 Converter。
4
记住 Feign 契约红线——不直接修改已发布 Feign 方法/路径/参数/返回；枚举只扩展不改既有语义；废弃要同时 @Deprecated + @deprecated Javadoc。
5
掌握租户隔离三件套——所有租户表数据访问必带 wsTenantId；wsTenantId 必须来自服务端可信上下文；租户转换必须走统一工具。

阅读路径：补 DDD/分层/SaaS 多租户背景 → 理解「新增强制/存量治理」生效方式 → 拆工程结构/契约/鉴权/数据库/MQ/并发六板块 → 闯关场景题 → 复盘。

02 零基础背景包

背景补充 1：DDD 多模块 vs 传统分层

背景补充

公司现有两套架构并存：DDD 多模块（client/api/application/domain/dependency/dal/bootstrap 等模块）和传统分层（feign/service/bootstrap 等）。规范允许并存，但同一个服务内部不能局部混入另一套。

为什么读本文需要它：工程结构章节的所有「按架构类型分层」规则都建立在你先认清楚自己服务是哪种架构之上。

背景补充 2：SaaS 多租户与 wsTenantId

背景补充

公司是 SaaS 厂商，一套代码服务多家客户（租户）。每张租户表都有 ws_tenant_id 字段做数据隔离，分片表还把它当分片路由键。数据访问漏带这个字段 = 跨租户数据泄露。

为什么读本文需要它：数据库、鉴权、Redis Key 多处规则都围绕 wsTenantId 展开，是全篇最高频红线。

背景补充 3：Feign 与微服务契约

背景补充

OpenFeign 是声明式 HTTP 客户端，服务间通过 Feign 接口互相调用。一旦接口发布，调用方可能在多个服务中依赖它，所以 Feign 方法的签名、路径、DTO 字段就是「公共契约」，破坏性修改会导致老调用方序列化或调用失败。

为什么读本文需要它：第 4 章「API、Feign 与契约」的核心是向后兼容，理解契约才能理解为什么禁止直接改方法签名。

背景补充 4：MUST / SHOULD 规范用语

背景补充

本文借用 RFC 关键词：MUST=绝对要求、MUST NOT=绝对禁止、SHOULD=默认采用（偏离需评估）、SHOULD NOT=默认避免。评审和发布门禁不得以「历史代码如此」为由放行新增违规。

为什么读本文需要它：每条规则的开头标记决定你能不能偏离，以及偏离要走什么流程。

03 原文问题定位

表面在讲什么？

8 大主题：工程结构与分层、命名与 Java 实践、API/Feign 契约、鉴权异常日志、数据库与事务、Redis 与 MQ、并发与外部调用与安全。

深层在回答什么问题？

「几十个 Java 微服务、上百号人协作，怎么写出可维护、不互相打架、不会跨租户泄密的代码？」

答案是「统一基线 + 分层职责 + 公共契约 + 服务端可信」：原文：新增代码强制执行 · 存量代码逐步治理。

作者为什么要写这篇？

版本号已到 1.5、37 页正文，是反复迭代出的工程契约。目的是消除「每个业务方法各自处理下游错误」「Controller 直接访问 Mapper」这类失控写法，把鉴权、租户、注入、危险数据库操作列为红线优先治理。

只记一个问题

「新增代码怎么写才合规？」——统一基线、按架构分层、Controller 轻量、每层用本层对象、Feign 向后兼容、wsTenantId 服务端确认、事务最小边界。

原文结构类型：主题簇 + 规则条目（8 个主题，每个主题下若干 MUST/SHOULD 规则，每条带正反例）

核心：8 大主题共同保证「可维护 + 不互相打架 + 不泄密」
主题1：工程结构与分层（2.x）

主题3：API Feign 契约（4.x）
路径前缀 /feign /bff、不直接暴露公网、专用 Request/Response + Result、参数校验、分页上限、向后兼容、枚举只扩展、废弃、时间ID协议
主题4：鉴权 异常 日志（5.x）

主题5：数据库 MyBatis 事务（6.x）
统一字段命名、合适类型唯一索引、无外键无触发器、兼容变更、wsTenantId、租户工具、显式字段、安全 WHERE、参数绑定、分页上限、CONCURRENTLY、编程式事务最小边界、不长耗时外部操作、不回滚外部资源
主题6：Redis MQ（7.x）
框架客户端可识别 Key、TTL≤24h、控制 BigKey、禁危险命令、缓存一致性按业务、标准信封、关键消息失败可处理、按业务幂等、框架重试死信
主题7：并发 外部 安全（8.x）
线程池受控、框架管上下文、锁最小范围、分布式锁有界释放、重试只用于幂等、不伪造下游成功、密钥不进仓库、防注入
节点关系说明：7 大主题是并列主题簇，不是因果链。每条规则下的 Positive/Negative Example 是例证关系。红线（鉴权、租户、注入、危险命令、可能损坏数据的操作）跨多个主题反复出现，是治理优先级最高的横切关注点。

05 核心判断与依据

判断1：新增代码强制执行 · 存量逐步治理

原文依据：原文 1.1：新增代码必须遵守 MUST、MUST NOT 规则；评审和发布门禁不得以「历史代码如此」为由放行新增违规

类型：判断。为什么重要：这是全文的生效方式。不能拿「老代码也这么写」当借口给新增违规开绿灯。存量违规要进可追踪治理清单按风险逐步改。

易误读：不是「存量代码必须一次性全改完」——按风险、影响范围、改造成本逐步治理。

判断2：Controller 保持轻量，不碰数据访问

原文依据：原文 2.2：Controller 和 Feign Controller 只负责协议入口、参数校验、鉴权编排、对象转换和调用应用服务

// 反例：Controller 直接访问 Mapper 并暴露 DO @PostMapping("/detail") public Result<CustomerDO> detail(@RequestBody CustomerDetailRequest request) { LambdaQueryWrapper<CustomerDO> wrapper = new LambdaQueryWrapper<>(); wrapper.eq(CustomerDO::getId, request.getId()); return ResultUtils.success(customerMapper.selectOne(wrapper)); }

类型：事实（原文明确列在 2.2 Negative Example）。反例的错：① Controller 直接 new Wrapper 访问 Mapper；② 把 DO（数据库对象）直接作为接口响应暴露。

判断3：Feign 契约只增不改、只扩不删

原文依据：原文 4.6：不得直接修改或删除任何已经存在的 Feign 方法、路径、HTTP 方法、参数类型、返回类型和既有 DTO 字段；不得以尚未发布、认为没有调用方或临时确认无调用方为理由进行破坏性修改

类型：判断（MUST NOT）。关键：「我认为没人调用」不能成为破坏性修改的理由。需要调整就新增 V2 契约，V1 在兼容期内保留。

判断4：wsTenantId 必须来自服务端可信上下文

原文依据：原文 5.1：数据访问使用的 wsTenantId 必须来自服务端登录或 Tenant 上下文；请求中携带的 tenantId、wsTenantId 只能用于兼容既有契约或与上下文做一致性校验，不得用于切换当前数据租户

客户端伪造请求体 {customerId: 100, wsTenantId: 999}，试图访问租户 999 的数据。如果服务端直接信任 request 里的 wsTenantId，一次合法登录就能变成跨租户访问。正确做法：从 LoginUser/可信上下文取 wsTenantId，request 里的值只用来做一致性校验。

判断5：事务最小边界 + 事务内不做长耗时外部操作

原文依据：原文 6.12：业务数据库事务使用 Spring 管理的编程式事务显式划定边界；不得新增 @Transactional

原文 6.13：数据库事务中不得执行长耗时 Feign、文件上传、消息等待、sleep 或无限批量循环

类型：判断（MUST + MUST NOT）。为什么重要：事务持有数据库锁和连接，Feign/文件上传这种不可控的外部调用放进去会拉长锁占用，且本地事务根本回滚不了它们。

判断6：Redis Key 强制 TTL ≤ 24 小时

原文依据：原文 7.2：所有 Redis Key 必须设置 TTL；自定义 TTL 最长不得超过 24 小时；不得创建永久 Key

  • Redis TTL 红线：≤ 24 小时，禁永久 Key
  • Big Key：String ≤ 10KB；Hash/List/Set/ZSet 元素 ≤ 3000
  • 危险命令：线上禁 KEYS / FLUSHALL / FLUSHDB
  • 新表公共字段：snowflake bigint 主键 + deleted + version + gmt_create + gmt_modified(timestamp(3))
  • 金额：最小货币单位整数或 BigDecimal，用 compareTo 比较
  • 禁反射复制：不得用 BeanUtils.copyProperties 复制业务对象
  • 对外时间格式：yyyy-MM-dd HH:mm:ss，不带时区

判断7：密钥不得进入仓库（任何形式）

原文依据：原文 8.7：密码、Token、AK/SK、私钥等真实凭证不得出现在代码、POM、YAML、文档、测试数据、日志、提交历史或任何其他仓库内容中

// 正确：从环境变量或密钥管理取 datasource: password: ${CUSTOMER_DB_PASSWORD} third-party: access-key: ${THIRD_PARTY_ACCESS_KEY}

06 关键概念拆解

概念1：分层对象（Request / DTO / Entity / DO / Response）

原文术语：每一层使用本层对象并在相邻层转换（2.6）

人话解释：不同层不能共用一个对象。Controller 接 Request，Service 吃 DTO，Repository 读写 DO（Data Object，对应数据库行），返回时再转 Response。每跨一层就用 Converter 显式转一次。

CustomerDTO dto = requestConverter.toDTO(request); CustomerEntity entity = customerService.create(dto); CustomerResponse response = responseConverter.toResponse(entity);

与其他概念的关系：类型后缀（3.2）规定类名要体现所在层——CustomerCreateRequest、CustomerCreateDTO、CustomerEntity、CustomerDO、CustomerCreateResponse。

原文 2.6 + 3.2

不要误解成：不是「随便起个 CustomerInfo 到处用」，那样字段边界无法判断。也禁止 BeanUtils.copyProperties 把 Request 直接拷成 DO 返回。

概念2：wsTenantId 与租户隔离

原文术语：wsTenantId（分库分表使用的 wsTenantId）

人话解释：租户在 SaaS 系统里的全局唯一编号。租户表的 SELECT/UPDATE/DELETE 必须带 ws_tenant_id 条件，分片表还用它做分片路由。漏带 = 数据跨租户泄露。

// 正例：查询带租户 + 主键 + 逻辑删除三条件 wrapper.eq(CustomerDO::getWsTenantId, wsTenantId) .eq(CustomerDO::getId, customerId) .eq(CustomerDO::getDeleted, 0); // 反例：只按主键删，证明不了租户隔离 customerMapper.deleteById(customerId);

与其他概念的关系：租户转换工具（6.6）解决 tenantId → wsTenantId 的映射，禁止业务自己缓存映射；鉴权（5.1）规定 wsTenantId 必须来自服务端可信上下文。

原文 6.5 / 5.1 / 6.6

概念3：统一 Result<T> 与错误码

原文术语：Result<T> / ResultUtils / 成功码 00000

人话解释：所有 BFF 和 Feign JSON 接口的统一响应外壳。成功时 code=00000。业务异常必须继承 BaseException，错误码由全局处理器统一映射，不得在异常消息里手工拼接错误码。

// 反例：手工拼错误码 + 普通 RuntimeException throw new RuntimeException("001999: customer missing"); // 正例：用错误码枚举 throw new CustomerServiceException( CustomerErrorCode.CUSTOMER_NOT_FOUND, "客户不存在");

原文 4.3 / 5.2

概念4：Spring 编程式事务（TransactionTemplate）

原文术语：编程式事务 / 不得新增 @Transactional

人话解释：项目统一用 TransactionTemplate 或 PlatformTransactionManager 显式开事务，禁止再写 @Transactional 注解，也禁止直接操作 JDBC Connection 或 MyBatis SqlSession 事务。原因：注解隐藏了事务边界，不符合项目显式控制方式。

transactionTemplate.executeWithoutResult(status -> { orderRepository.save(order); orderChangeLogRepository.saveCreateLog(order); });

原文 6.12

不要误解成：不是「所有写操作都要开事务」。单条数据库写依赖数据库自身事务即可，只有必须原子完成的多步本地数据库操作才显式开。

概念5：Feign 向后兼容（V1/V2 并存）

原文术语：保持 Feign 和 DTO 向后兼容（4.6）

人话解释：要改契约不能直接改老方法，而是新增 V2 方法（新路径 + 新 DTO），V1 标 @Deprecated 继续可用，直到所有调用方迁移完且 V2 经过一个稳定发布周期，才能删 V1。

@Deprecated @PostMapping("/feign/v1/customer/query") Result<CustomerV1Response> queryV1(CustomerQueryV1Request request); @PostMapping("/feign/v2/customer/query") Result<CustomerV2Response> queryV2(CustomerQueryV2Request request);

原文 4.6 + 4.8

概念6：枚举只扩展不改既有语义

原文术语：枚举值只允许扩展，不改变既有语义（4.7）

人话解释：枚举值（如状态码）已经发布后，不能删、不能改值、不能复用旧值表达新含义。要加新状态就新增一个枚举常量，旧值的编号和含义保持不变。否则历史数据库行和旧调用方会把状态解释成相反含义。

// 正例：新增 ARCHIVED，旧值不动 public enum CustomerStatus { ENABLED(1), DISABLED(2), ARCHIVED(3); } // 反例：把 1 的含义从 ENABLED 改成 DISABLED public enum CustomerStatus { DISABLED(1), ENABLED(2); // 历史数据全错 }

原文 4.7

09 误解与边界

误解1：「老代码也这么写，所以我能这么写」

为什么容易误解：「存量代码就是这样」看起来是合理借口。

原文真正说了什么：新增代码必须遵守 MUST/MUST NOT；评审和发布门禁不得以「历史代码如此」为由放行新增违规。存量违规进治理清单按风险逐步改。

如何避免：写新代码前查规范；看到老代码违规时记录到治理清单，但不要模仿。

误解2：「Validator 可以查数据库校验业务状态」

为什么容易误解：校验注解看起来什么都能做。

原文真正说了什么：Validator 只能进行纯参数校验，不得查询数据库、调用远程服务或修改数据。资源归属、数据库状态、权限、业务状态等依赖外部数据的规则，必须在 Service 业务入口用 Java 代码校验。

如何避免：@NotBlank/@Size 这类结构约束用注解；查重、查权限、查状态放 Service 里写 Java。

误解3：「事务回滚了，Redis/MQ/Feign 也跟着回滚」

为什么容易误解：都写在同一个 transactionTemplate 里看着像一起回滚。

原文真正说了什么：不得假设数据库事务能回滚 Redis、ES、MQ 或第三方系统。已经投递的消息不会随数据库回滚撤回；消费者可能早于数据库提交收到消息。

如何避免：跨资源一致性用消息重试（消费者收到时数据不可见就抛可重试异常）、状态机、幂等或补偿。

误解4：「BeanUtils.copyProperties 省事，能用就用」

为什么容易误解：Spring 里到处都见这个工具。

原文真正说了什么：MUST NOT 不使用 BeanUtils.copyProperties 或 BeanUtil.copyProperties 复制业务对象，改用显式 Converter 或 Builder。原因：字段语义、忽略项、类型转换都不可见，新增字段会被悄悄复制。

如何避免：写显式 Converter，每个字段映射可搜索、可评审。

误解5：「事务里发 MQ 失败就 catch 一下记日志，业务算成功」

为什么容易误解：不想让消息失败影响主流程。

原文真正说了什么：关键消息发送必须检查结果，不得捕获发送失败后仍按成功处理。建议业务数据库写入和 MQ 发送放同一个事务，发送失败抛异常回滚。

如何避免：区分关键消息 vs 非关键埋点。关键消息必须可处理；非关键埋点（如 event-boot-starter）才允许失败只记日志。
