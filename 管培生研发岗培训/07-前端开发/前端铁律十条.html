01 学习目标与阅读路径

这是一份写给"刚学完前端基础、第一次进微盛项目"的同学的拆解地图。它要讲清一件事：这十条铁律每一条都不是随便定的，背后都有"违反了会出什么事"的真实代价。读完这一章，你能做到下面五件事。

1
能背出 10 条铁律的核心：组件复用、禁改全局、移动端保活、TS+选项式、scoped 防污染、REM+FLEX、多状态、API 规范、提测上线验证、基于 master 建分支。
2
能分清"禁止做"和"应该做"：哪些是红线（禁改全局样式、禁合并 release 到需求分支、禁用组合式/JSX），哪些是推荐做法（用 v-loading、用 scoped、用选项式）。
3
能说清每条"为什么这么规定"：不是死记，而是理解——为什么禁改全局样式？因为会污染所有页面；为什么用 REM？因为移动端屏幕尺寸碎片化。
4
能指出至少 3 个新手最常踩的坑（如在 release 上改代码、用组合式 API 写业务、改了 main.ts 觉得"就改一行没事"、接口数组没判空导致页面白屏）。
5
能提出 1 个追问：例如"既然选项式和组合式都能实现功能，团队为什么统一禁用组合式？统一风格到底换来什么？"
阅读路径（按顺序）

先在 02 补 8 个零件 → 在 03/04 看清"这十条在解决什么、整体怎么搭" → 在 05/06 抓住 5 条核心判断和 10 条逐条拆解 → 在 07 自己提问 → 在 08 闯 8 道闭环题 → 在 09/10 看边界 → 在 11 出报告。

02

零基础背景包

在拆铁律前，先装 8 个最基本的零件。每个都标了"背景补充"——它帮你读懂铁律，但不是铁律本身的规定，而是帮你建立"企业级前端到底在干什么"的常识。

背景补充 1 · 组件库（component library）

组件库是一套预先写好、经过测试的 UI 组件集合（按钮、表格、弹窗、日期选择器……）。微盛有"基础组件"和"业务组件"两层。大家统一用同一套，意味着全公司的按钮长得一样、行为一样。

类比：组件库 ≈ C 语言的标准库函数（printf/strcpy），你不重写它，直接 #include 调用。
为什么现在需要知道：铁律 1 要求"统一使用组件"，铁律 2 禁止"修改组件实现"——不懂组件库是什么，就读不懂为什么不能改它。
背景补充 2 · TypeScript（TS）

TS 是给 JavaScript 加上类型标注的超集。变量、参数、返回值都标明类型，编译期就能发现"把字符串当数字用"这种错误，不用等到运行时白屏。

类比：TS ≈ 给 JS 加上 C 语言的类型检查；JS 的变量是 void*，TS 的变量是 int*/char*。
为什么现在需要知道：铁律 4 规定"前端标品项目均使用 TS 语言"，铁律 8 要求"用 swagger 生成 TS 定义"。
背景补充 3 · Vue 的选项式 API vs 组合式 API

Vue 组件有两种写法：选项式（Options API）把代码分到 data/methods/computed 这些"选项"里；组合式（Composition API）用 setup() 自由组织逻辑。组合式更新、更灵活，但风格发散；选项式老、但结构固定、好读。

类比：选项式 ≈ 填一张固定格式的表（姓名/年龄/地址各一栏）；组合式 ≈ 一张白纸自由发挥。表好对齐，白纸好创作。
为什么现在需要知道：铁律 4 明确"业务代码优先 template、选项式，而非 JSX、render 函数、组合式 API"——这是团队风格统一的选择，不是技术优劣。
背景补充 4 · scoped 样式与样式污染

网页里所有 CSS 是全局生效的：你写一个 .title{color:red}，全页面所有 class 为 title 的元素都会变红。Vue 的 <style scoped> 给当前组件的元素加上唯一属性标记，让样式只作用于本组件，不漏出去。

类比：scoped ≈ 给你的样式加个命名空间（namespace），别人的 .title 和你的 .title 互不干扰。
为什么现在需要知道：铁律 5 整条都在讲"避免样式污染"——scoped + 唯一 class 名是两道防线。
背景补充 5 · REM 与移动端适配

px 是绝对像素，REM 是相对"根元素字号"的单位。手机屏幕尺寸碎片化（375px/414px/各种分辨率），用 px 写死会导致大屏字小、小屏字大。REM 让所有尺寸随根字号缩放，一套样式适配所有屏。

类比：px ≈ 固定字号 12pt 打印；REM ≈ "按页面宽度百分比"缩放，屏越大字越大但比例不变。
为什么现在需要知道：铁律 6 规定"移动端字体/尺寸适配使用 REM"。
背景补充 6 · keepAlive 与页面保活

默认情况下，离开一个页面它就被销毁、回来时重新创建（列表滚回顶部、输入清空）。keepAlive 是"保活"——离开时把页面缓存起来，回来时恢复到离开时的状态（滚动位置、表单内容都在）。

类比：keepAlive ≈ 把当前页面"冻结"存硬盘，回来时"解冻"恢复；不保活 ≈ 关掉程序再重开，一切归零。
为什么现在需要知道：铁律 3 规定"移动端列表页面保活使用 keepAlive:auto"——列表页保活是体验刚需。
背景补充 7 · Swagger 接口文档

Swagger 是一种标准化的接口文档格式（通常是一个在线页面），列出每个接口的 URL、请求参数、返回字段的类型和含义。前端可以拿它自动生成 TS 类型定义，不用手抄。

类比：Swagger ≈ 函数的 .h 头文件——告诉你函数名、参数类型、返回类型，但实现 .c 在后端那边。
为什么现在需要知道：铁律 8 要求"需向后端索取 swagger 接口文档生成 TS 定义"——这是前后端协作的契约。
背景补充 8 · 特性分支（feature branch）工作流

多人协作时，大家不在 master（主线）上直接改代码，而是每人/每需求拉一条独立分支（feature-xxx），改完再合并回主线。这样多个需求互不干扰，主线始终可发布。

类比：特性分支 ≈ 每人一份源码副本各自改，改完再 diff 合并到主目录；release 分支 ≈ "这一版要一起交的作业本"。
为什么现在需要知道：铁律 10 整条讲分支策略——基于 master 建需求/bugfix 分支，禁止合并 release/dev 进来。
03

原文问题定位

表面在讲什么？

一份清单：前端写代码时该用什么组件、什么语言、什么写法、怎么处理状态、怎么对接接口、怎么管分支、上线前要做什么。事实

深层在回答什么问题？

几十个前端一起维护几十个项目，怎么保证每个人写出来的代码风格一致、互不污染、可维护、可追溯？这十条铁律本质上是在解决团队协作的标准化问题——把"个人偏好"统一成"团队约定"，把"容易出错的点"提前堵死。判断

前端铁律十条：1.统一使用组件；2.禁止修改全局；4.使用TS+选项式；5.scoped防污染；10.基于master建分支……
读者如果只记一个问题，应该记哪个？

每条铁律"为什么这么规定"——它防止的是哪种真实事故？把"为什么"想通了，十条就不是死记的清单，而是一套互相支撑的工程逻辑。推论

十条按"规定性质"分三类

代码规范类（怎么写代码）：1、2、4、5、6、7、8 —— 组件、TS、scoped、REM、多状态、API；
分支规范类（怎么管分支）：10 —— 基于 master 建需求/bugfix 分支；
质量保障类（怎么验证不出事）：3、9 —— 移动端保活机制、提测上线验证。这三类覆盖了"写、管、验"全流程。

04

原文结构地图

判断结构类型：主题簇（一组并列的规则）。十条铁律不是流水线，而是围绕"团队标准化"这个主题的并列约定。但它们内部有逻辑分组：管代码写法的、管分支的、管质量验证的。

主题：前端团队标准化（十条铁律） （主题簇）
  ├─ A. 代码规范类（7 条 · 怎么写代码）
  │    ① 统一使用前端基础/业务组件
  │    ② 禁止修改组件实现、全局样式、全局文件（public/、根目录、src/utils、main.ts）
  │    ④ TS 语言 + 可读性 + 语义命名 + 优先 template/选项式（非 JSX/组合式）
  │    ⑤ scoped + 唯一 class 名（防样式污染）
  │    ⑥ REM 适配 + FLEX 布局 + 全局变量/class
  │    ⑦ 多状态处理（初始化/加载中/失败/无数据）+ v-loading/loading 防重复提交
  │    ⑧ API 规范（接口数≤2、swagger 生 TS、变更评估影响、数组判空、错误透出）
  ├─ B. 分支规范类（1 条 · 怎么管分支）
  │    ⑩ 基于 master 建需求/bugfix 分支；禁止合并 release/dev 进需求分支；冲突协商处理
  └─ C. 质量保障类（2 条 · 怎么验证不出事）
      ③ 移动端列表保活 keepAlive:auto + pageStack 通讯/清理
      ⑨ 提测前 UI 高精度还原 + P0/P1 自测；上线后线上验证主流程 + 通知 QA
三类规则的关系

代码规范类是日常写代码的约束（最高频，7 条都在管这个）；分支规范类是多人协作的约束（防代码互相覆盖、防把测试代码带上线）；质量保障类是交付前的兜底（防提测翻车、防上线后才发现问题）。三类合起来覆盖"写→合→交"全链路。

05

核心判断与依据

从十条里挑出 5 条最硬、最容易踩的判断。每条都附原文依据和"为什么这么规定"。

判断 1 · 禁止修改全局样式、全局文件（铁律 2）

public/、项目根目录、src 根目录、src/utils、main.ts 这些是"全局共享文件"，一处改动会影响所有页面所有需求。哪怕"就改一行"，也可能让别的需求页面莫名崩掉。判断

禁止修改组件实现、全局样式、全局文件，包括 public/、项目根目录、src 根目录、src/utils 目录下的文件，main.ts 文件。

为什么重要：这是十条里最重的红线。全局文件 = 所有页面的地基，动地基 = 所有楼都晃。新人最常犯的就是"我就改个 utils 里的工具函数，没事吧"——结果别的需求正好依赖旧行为。

判断 2 · 业务代码优先选项式/template，禁用组合式/JSX（铁律 4）

技术上组合式 API 和 JSX 都能实现功能，但团队统一选选项式 + template，是因为它们结构固定（data/methods/computed 各归各位）、好读好交接。组合式 setup() 太自由，十个人写出十种结构。判断

业务代码优先使用 template、选项式，而非 JSX、render 函数、组合式 API。

易误读：这不是说组合式"落后"或"不能用"——它是风格统一的选择，换来的是"任何人接手任何代码都能快速看懂"。

判断 3 · 接口数组必须判空（铁律 8）

后端返回的数据不保证永远是数组——可能是 null、undefined、甚至因异常返回对象。前端直接 list.map() 就会白屏报错。判空（(list||[]).map() 或 v-if）是兜底。判断

接口中的数组类型需做判空处理。接口错误信息需透出。

为什么重要：这是线上白屏事故的高发源。后端一改字段、一返回 null，前端没判空就直接崩给用户看。

判断 4 · 禁止合并 release/dev 分支到需求分支（铁律 10）

release 分支上混着"这一版所有需求"的代码，dev 分支可能是脏的。把它们合并进你的需求分支，等于把别人未上线、未测试的代码带进你的需求，发布时无法追溯"这个 bug 是哪个需求引入的"。判断

基于 master，以需求为单位，建立需求/bugfix 分支；禁止合并 release-xxx/dev 分支到需求分支。

为什么重要：这条保证"每个需求分支只包含本需求的代码"，是上线可追溯、出问题能精准回退的前提。

判断 5 · 提测前必须 UI 高精度还原 + P0/P1 自测（铁律 9）

提测不是"我写完了甩给测试"，而是"我已经自测过主流程能跑通、UI 还原到设计稿级别"。把低级 bug 留给测试发现，会反复打回、拖慢整个版本。判断

提测前需完成 UI 高精度还原，P0/P1 测试用例自测通过。上线后开发者需线上验证，重点验证主流程并通知 QA 验证。
质量责任链：开发自测（提测前）→ QA 测试（提测后）→ 开发线上验证（上线后）
06

关键概念拆解

逐条拆解 10 条铁律。每条讲清三件事：规定什么 / 为什么 / 违反了会怎样。这是整章的重点——不是让你背，是让你懂。

铁律 1 · 统一使用前端基础/业务组件
规定什么页面上所有 UI 元素（按钮、表格、弹窗、表单项……）都用团队提供的基础组件库或业务组件库，不要自己手写一个"长得差不多"的。
为什么①保证全产品视觉和交互一致（用户在每个页面看到的按钮行为都一样）；②组件库经过测试和迭代，比自己手写的健壮；③ bug 修在组件库一处，全局生效。
违反了会怎样你手写一个按钮，样式/交互和别人的不一样，用户体验割裂；按钮的 bug 你修一处，别人那没修，各页面行为分裂。
统一使用前端基础｜业务组件。
铁律 2 · 禁止修改组件实现、全局样式、全局文件
规定什么不准动：组件库源码、全局 CSS、public/ 目录、项目根目录、src 根目录、src/utils 目录、main.ts。这些是"所有人共享的地基"。
为什么这些文件被所有页面、所有需求共用。你改一处，影响的是整个项目几十个页面。你以为"改一行没事"，可能正好破坏了别的需求依赖的行为。
违反了会怎样你改了 main.ts 引入一个全局副作用，别人的页面莫名其妙挂了，排查半天才发现是你这行；上线后别的需求跟着出 bug，责任难划分。
怎么办需要的逻辑写在自己需求页面/组件里；确实需要全局能力，走团队评审统一加。
禁止修改组件实现、全局样式、全局文件，包括 public/、项目根目录、src 根目录、src/utils 目录下的文件，main.ts 文件。
铁律 3 · 移动端列表保活 keepAlive:auto + pageStack
规定什么移动端列表页用 keepAlive:auto 保活（离开再回来保持滚动位置和状态）；用 pageStack 机制实现页面间通讯和缓存清理。
为什么移动端列表→详情→列表是最高频路径。不保活，用户从详情返回列表，列表重新加载、滚回顶部、筛选条件丢失，体验极差。保活后返回即恢复，符合 App 直觉。
违反了会怎样用户每次返回都看到"加载中"再重新滚动找刚才那条，体验像 2010 年的 WAP 网站；缓存不清理还会内存泄漏。
移动端列表页面保活使用 keepAlive:auto；使用 pageStack 实现页面间通讯及缓存清理。
铁律 4 · TS 语言 + 可读性 + 语义命名 + 优先选项式/template
规定什么①标品项目一律用 TypeScript；②代码要有可读性；③变量、style class 命名语义化（叫 userList 不叫 arr1、叫 login-btn 不叫 btn-red）；④业务代码用 template + 选项式，不用 JSX、render 函数、组合式 API。
为什么TS 让类型错误在编译期暴露；语义命名让接手的人不看注释也懂；选项式/template 结构固定（data/methods/computed 各归各位），团队任何人看任何代码都能快速上手。组合式/JSX 太自由，十个人十种写法。
违反了会怎样用 JS 不用 TS，运行时才发现字段拼错；用 a/b/tmp 命名，三个月后自己也看不懂；用组合式 setup 写业务，接手的人要花半天理清你的逻辑结构。
前端标品项目均使用 TS 语言；代码具有可读性；变量、style class 命名语义化；业务代码优先使用 template、选项式，而非 JSX、render 函数、组合式 API。
铁律 5 · 避免样式污染：scoped + 唯一 class 名
规定什么①组件加 <style scoped>；②页面/组件根元素加唯一 class 名；③组件外容器（如 Element 弹窗）加唯一 class 名。
为什么网页 CSS 默认全局生效，你的 .title{} 会影响所有页面的 .title。scoped 给本组件样式加作用域；唯一 class 名（如 user-list-page）是第二道防线，即使 scoped 失效也不会撞名。弹窗这类"挂到 body 上"的组件，scoped 管不到，必须靠外容器唯一 class 兜底。
违反了会怎样你写的 .active{color:red} 漏到全局，别的页面某个本不该红的元素变红了，排查到崩溃；弹窗样式互相覆盖，A 弹窗的按钮样式跑到 B 弹窗上。
避免样式污染：添加 style scoped；页面/组件根元素添加唯一 class 名；组件外容器添加唯一 class 名，如 Element 弹窗。
铁律 6 · 移动端 REM 适配 + 各端 FLEX 布局 + 全局变量/class
规定什么①移动端字体/尺寸用 REM（不用 px 写死）；②所有端（移动/H5/PC）统一用 FLEX 布局；③颜色、间距、字号等用全局变量/全局 class，不要每个页面硬编码。
为什么移动端屏幕碎片化，px 写死会导致大屏字小、小屏字大；REM 随根字号缩放，一套样式适配所有屏。FLEX 是现代布局标准，对齐/分布/响应式都好写。全局变量（如 --primary-color）让换肤、统一改色一处生效。
违反了会怎样用 px 写死，iPhone 大屏字小看不清、小屏挤压；每页硬编码颜色，产品说"主色换个深绿"，你要改几十个文件。
移动端字体/尺寸适配使用 REM。各端统一使用 FLEX 布局。使用全局变量/class。
铁律 7 · 正确处理页面多状态 + v-loading 防重复提交
规定什么①每个数据页面要处理四种状态：初始化、加载中、加载失败、无数据；②不能在初始化状态就显示"无数据"或错误的默认值；③加载失败状态要能重置；④按钮/组件加载中用 v-loading，WsTable 用 loading 属性，防止用户重复点击重复提交。
为什么用户点进页面到数据展示之间有网络延迟。没"加载中"态，用户以为卡死；接口失败没"失败"态，用户看到空白以为没数据；初始化时显示假数据会误导。loading 期间禁用按钮，防止用户连点导致重复下单/重复请求。
违反了会怎样页面白屏用户疯狂刷新；接口报错了页面还显示旧数据；用户连点提交按钮，后台收到 3 个重复订单。
四状态：初始化 → 加载中 →（成功→有数据/无数据 | 失败→加载失败 → 重试）
正确处理页面多状态，初始化状态、加载中、加载失败、无数据……组件、按钮加载中使用 v-loading 避免重复提交；WsTable 加载中使用 loading 属性。
铁律 8 · API 规范（接口数、swagger、判空、错误透出）
规定什么①一个页面内容数据接口典型 1 个、最多 2 个（不要一页面发 10 个请求）；②向后端要 swagger 文档生成 TS 类型定义；③接口 URL/字段类型变更要评估影响范围；④接口返回的数组必须判空；⑤接口错误信息要透出给用户（不要吞掉）。
为什么接口越多页面越慢、出错点越多；swagger 生 TS 保证前后端类型契约一致、不用手抄易错；变更不评估会导致依赖方崩；数组不判空是白屏首因；错误吞掉用户不知道发生了什么、无法反馈问题。
违反了会怎样一个页面调 8 个接口，慢且一个失败全乱；手抄类型拼错字段名编译不报错运行时 undefined；后端把数组改成 null，你没判空，整个页面白屏；接口 500 了你还显示"操作成功"。
API 规范：页面内容数据接口数量典型情况一个，最多二个。需向后端索取 swagger 接口文档生成 TS 定义。接口 URL/字段类型变更需考虑影响范围。接口中的数组类型需做判空处理。接口错误信息需透出。
铁律 9 · 提测前 UI 高精度还原 + P0/P1 自测；上线后线上验证
规定什么①提测前 UI 要高精度还原设计稿（不是"差不多就行"）；②P0/P1 级测试用例开发自己跑通再提测；③上线后开发要在线上环境验证主流程，并通知 QA 验证。
为什么提测质量决定版本效率。低级 bug 留给 QA，反复打回拖慢所有人；UI 不还原，设计师打回、QA 报 bug，三倍返工。上线后线上环境≠测试环境（数据量、配置、依赖都不同），必须真实验证主流程，否则用户最先撞见 bug。
违反了会怎样提测一坨低级 bug，QA 怨声载道、版本延期；上线后主流程挂了，全公司救火。
提测前需完成 UI 高精度还原，P0/P1 测试用例自测通过。上线后开发者需线上验证，重点验证主流程并通知 QA 验证。
铁律 10 · 基于 master 建需求/bugfix 分支；禁合 release/dev
规定什么①每个需求/bug 都基于 master 拉一条独立分支；②禁止把 release-xxx 或 dev 分支合并进需求分支；③合并产生冲突必须联系相关人员一起协商，不能自己强行覆盖解决。
为什么master 是稳定的已上线代码基准，从它拉分支保证起点干净。release 上混着本版所有需求的代码、dev 可能脏，合进来会污染你的需求、让发布无法追溯"这行是哪个需求加的"。冲突强行覆盖，可能静默丢掉别人的代码。
违反了会怎样把 release 合进需求分支，你的需求带上了别人未上线的代码，发布时如果别的需求延期/取消，你的代码被一起卡住或回退；冲突自己强解覆盖了同事的实现，事故。
基于 master，以需求为单位，建立需求/bugfix 分支；禁止合并 release-xxx/dev 分支到需求分支。代码合并产生的冲突必须联系相关人员一起协商处理。
07

苏格拉底式阅读关卡

不直接给答案，自己想。参考答案在每题下方，但请先停 30 秒再展开。这一节专挑"为什么"类的问题。

Q1 · 入门为什么移动端要用 REM，而不是 px？
因为手机屏幕尺寸碎片化（375px / 414px / 各种分辨率）。px 是绝对值，写死后大屏显得字小、小屏挤压。REM 相对根字号缩放，根字号又会随屏幕宽度变化，所以一套 REM 样式能等比例适配所有屏，"看起来比例不变、只是整体放大缩小"。
提示：想想同一套样式在 iPhone SE 和 iPhone Pro Max 上的差别。
Q2 · 入门为什么禁止把 release 分支合并到需求分支？
release 分支上混着这一版所有需求的代码，而你要的是"只包含本需求的代码"。把 release 合进来，等于把别人未上线、未测试完的代码带进你的需求。后果：①发布时无法精准追溯 bug 来源；②别的需求延期/取消时，你的代码可能被一起回退。需求分支必须保持"只装自己这一份"。
Q3 · 进阶为什么接口返回的数组一定要判空？后端不是保证返回数组吗？
因为运行时太多意外：后端异常可能返回 null、网络超时可能返回 undefined、字段被改、缓存脏数据、网关截断……任何一种让数据不是数组，你直接 list.map() 就抛 TypeError、整个页面白屏。判空（(list||[]).map()）是前端自己的最后兜底，不依赖"后端一定守约"。守约是理想，判空是工程。
提示：回到 05 判断 3 + 06 铁律 8。
Q4 · 进阶团队为什么统一用选项式 API、禁用组合式？组合式不是更先进吗？
"先进"是技术演进角度，团队选型还要看协作成本。组合式 setup() 自由度高，十个人能写出十种结构，接手成本高；选项式把代码固定分到 data/methods/computed，结构统一，任何人接手都能快速定位。团队项目是几十人长期协作的资产，风格统一带来的可维护性 > 单个开发者的表达自由。这不是技术优劣，是工程取舍。
Q5 · 进阶scoped 已经能限制样式作用域了，为什么还要给根元素加唯一 class 名？
因为 scoped 不是万能的。①有些场景 scoped 管不到——比如 Element 的弹窗、抽屉这类组件会把 DOM 挂到 body 根节点下，脱离了当前组件的作用域，scoped 对它失效；②scoped 编译产物在极端情况下可能重复。所以唯一 class 名（如 user-list-page）是第二道防线：即使 scoped 失效，靠这个全局唯一的命名也不会和别人撞。两道防线一起，才能真的防污染。
Q6 · 深度"我就改 main.ts 一行，加个 console.log 调试，应该没事吧？"——这句话错在哪？
错在把全局文件当成了局部文件。main.ts 是整个应用的入口，所有页面都依赖它初始化。你加一行 console.log 看似无害，但：①它会在所有页面执行，污染全局日志；②忘记删，上线后每个用户每次操作都打印，影响性能；③更重要的是，一旦开了"全局文件可以改"的口子，下次别人也会改，最后全局文件变成多人混杂的雷区。调试应该在自己的页面/组件里做。
提示：注意 06 铁律 2 列出的禁改清单里 main.ts 在内。
Q7 · 深度为什么"加载失败"状态必须能重置？不能失败后就一直显示错误吗？
因为用户会重试。页面加载失败显示了"加载失败，点击重试"，用户点了重试，页面应该重新进入"加载中"状态、再请求一次。如果失败状态不重置，用户点了重试但页面还停在"失败"（因为状态没变回 loading），就会以为按钮坏了。正确做法：每次发请求前，先把状态置回"加载中"，成功再置"有数据/无数据"，失败再置"加载失败"。状态机要能正向走、也能重置回走。

09

误解与边界

误解 1 · "改个 main.ts / utils 就一行，应该没事"
为什么容易误解本地调试时确实"改一行就能跑通"，看不出影响。
原文真正说了禁止修改 main.ts、src/utils、public/、根目录等全局文件——它们是所有页面共享的地基。
原文没有说"改一行可以、改多行不行"——只要是全局文件，一行也不行。
如何避免所有逻辑写在自己需求页面/组件里；调试代码留在自己分支本地，不提交；确需全局能力走团队评审统一加。
误解 2 · "组合式 API 更先进，业务里也能用"
为什么容易误解Vue 3 主推组合式、社区都在夸，"先进 = 应该用"。
原文真正说了业务代码优先 template、选项式，而非 JSX、render 函数、组合式 API。
原文没有说"组合式落后不能用"——这是团队风格统一的选择（结构固定、好交接），不是技术优劣判断。
如何避免业务代码一律选项式 + template；想用组合式先和团队对齐，不擅自引入。
误解 3 · "后端说返回数组，前端就不用判空了"
为什么容易误解接口文档写的是 Array，后端也"承诺"返回数组，看起来没必要判。
原文真正说了接口中的数组类型需做判空处理——这是硬性规定。
原文没有说"后端保证了就不用判"——恰恰因为运行时有太多意外（异常、超时、字段变更），才必须判。
如何避免所有接口数组统一 (list||[]).map() 或 v-if="list && list.length" 兜底，不依赖后端守约。
误解 4 · "release 分支也是分支，把代码合到需求分支更全"
为什么容易误解觉得"多合一点代码进来更完整、能跑就行"。
原文真正说了禁止合并 release-xxx/dev 分支到需求分支；需求分支基于 master 建立。
原文没有说"合进来更全更好"——release 上是本版所有需求的混合代码，合进来污染需求、让发布无法追溯。
如何避免需求分支永远只基于 master；需要的别人代码等它合进 master 后再同步；冲突联系相关人员协商。
误解 5 · "页面有数据就显示，没有就空着，不用专门处理状态"
为什么容易误解本地测试数据正常，看不出空状态/失败态的问题。
原文真正说了必须处理初始化、加载中、加载失败、无数据四种状态；不能初始化就显示无数据或错误默认值；失败态要能重置。
原文没有说"有数据就行，其他不用管"——加载中和失败态直接影响用户体验和事故排查。
如何避免每个数据页面都画四态：骨架屏/转圈（加载中）、空态插画（无数据）、错误+重试（失败）、内容（成功）。

背景知识缺口

要彻底吃透这十条，建议补这 4 个背景。现在不补也行，遇到不懂的再回头看。

缺口 1 · Vue 3 选项式 vs 组合式的本质区别

铁律 4 禁用组合式，但要彻底理解"为什么"，建议补：选项式 API 的 data/methods/computed/watch 是怎么组织的、this 指向什么；组合式 setup() 为什么自由、ref/reactive 怎么用。为什么重要：懂了两者的结构差异，才懂"选项式结构固定好交接"不是空话——它是几十人协作时的真实诉求。

缺口 2 · scoped 样式的编译原理

建议补：Vue 的 scoped 在编译时给元素加了什么（data-v-xxxxxx 属性）、CSS 选择器怎么被改写成 .title[data-v-xxxxxx]；为什么挂到 body 的组件（弹窗/抽屉/消息）scoped 失效。为什么重要：理解了 scoped 的边界，才懂铁律 5 为什么除了 scoped 还要"唯一 class 名"做第二道防线。

缺口 3 · keepAlive 的缓存机制

建议补：Vue keep-alive 组件的 include/exclude/max 怎么工作；保活的组件实例存在哪、什么时候被销毁；keepAlive:auto 这种约定式保活具体匹配什么规则；pageStack 这种页面栈机制怎么管理缓存生命周期。为什么重要：铁律 3 的 keepAlive:auto 和 pageStack 是移动端体验的核心，懂了机制才能正确触发清理、避免内存泄漏。

缺口 4 · Git 特性分支工作流与冲突解决

建议补：为什么从 master 拉分支而不是从别的分支；fast-forward 和三方合并的区别；merge 冲突怎么手动解决；为什么强推/覆盖解冲突危险。为什么重要：铁律 10 的"基于 master 建分支、禁合 release/dev、冲突协商处理"全是 Git 工作流常识，懂了 merge 才懂为什么这么规定。

可以暂时不补的

Element/移动端组件库每个组件的具体 API、REM 换算的具体 px 值、swagger 在线编辑器用法——这些是工具操作层，用到查文档即可，不影响理解十条铁律的骨架。
