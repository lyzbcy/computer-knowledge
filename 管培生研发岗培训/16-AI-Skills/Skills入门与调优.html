02

零基础背景包

背景补充 TAPD

腾讯的项目管理工具，公司用它管需求、任务、迭代、缺陷和工时。「交付池」「产研池」是里面的项目池分类。

为什么现在需要知道：本章的 Skill 案例（TAPD Skill）都围绕它展开。

背景补充 CUA（Computer Use Agent）

让 AI 像人一样操作电脑界面：读页面、找按钮、点击、输入，再根据页面变化判断是否成功。

为什么现在需要知道：它是「没有稳定 API 时操作网页/桌面」的兜底能力，和 Skill 常配合使用。

背景补充 召回率（Recall）与精确率（Precision）

召回率：该找出来的对象里，实际找到了多少（漏得越少越高）。精确率：找出来的对象里，真找对了多少（误判越少越高）。两者常常此消彼长。

为什么现在需要知道：SkillOpt 调优案例的核心就是「召回优先」带来的指标涨跌。它不是本文的主张，只是帮助你读懂原文。

背景补充 FN 与 FP

FN（假阴性）= 漏判：该抓到的没抓到。FP（假阳性）= 误判：不该抓的抓了进来。

为什么现在需要知道：案例里「漏召回 266→73 条」是 FN 下降，「误判 187→298 条」是 FP 上升。

背景补充 train / dev / test 集

机器学习把标注样本分成训练集、调试集和测试集；test 集只用来最终评估，不参与调参，指标才有说服力。

为什么现在需要知道：SkillOpt 用 6000 条样本按 3600/1200/1200 切分。

原文问题定位

表面在讲什么

Skill 的定义和结构、公司常用 Skill 清单、CUA 能力、TAPD Skill 的创建与测试，再加 SkillOpt 客户意向识别的调优案例。事实

深层在回答什么问题

两个问题。第一：「重复工作怎么交给 AI 一次讲清、次次照做？」——答案是把公司口径、操作顺序和工具调用打包成 Skill。第二：「一个能跑的 Skill 怎么变成贴合业务目标的 Skill？」——答案是先定业务目标，再用样本、错题和指标验证每一轮改动。判断

原文依据（Skill调优 第2页）：「Skill 调优不是把提示词写长，而是把业务目标变成可验证的判断顺序。」

如果只记一个问题

记这个：这次调优更怕漏人还是更怕误判？——目标不同，规则取舍完全不同；v5 选了召回优先，代价是候选池更宽，所以要讲清适用位置。

05

核心判断与依据

判断1：重复、稳定、可检查的工作适合做成 Skill

核心判断：不是所有工作都适合封装；输入、步骤和输出比较固定、结果可检查的才适合。讨论产品方向、一次性生产数据修复不适合。

原文依据（Skill教程 01）：「重复出现、步骤相对稳定、结果可以检查的工作，最适合整理成 Skill。」

判断 为什么重要：防止为了用 Skill 而用 Skill。误读：把 Skill 当功能清单，什么都封装。

判断2：Skill 把公司口径、操作顺序和工具调用放在一起

核心判断：只有工具时 Codex 能调 TAPD 却不知道交付池对应哪个项目；只有 Prompt 时每个人描述方式不同。Skill 解决的是「口径不统一 + 步骤不固化」。

原文依据（Skill教程 02）：「Skill 把公司口径、操作顺序和工具调用放在一起。」

判断 为什么重要：这是 Skill 区别于 Prompt/Tool 的本质。误读：Skill 只是更长的 Prompt。

判断3：description 决定 Skill 什么时候被加载

核心判断：Skill 先暴露名称和描述，匹配任务后再读取完整 SKILL.md；描述过窄触发不到，过宽会让无关任务也加载。

原文依据（Skill教程 03）：「description 很重要：它既要说明能做什么，也要写出常见触发场景。描述过窄会触发不到，描述过宽会让无关任务也加载该 Skill。」

判断 为什么重要：description 是 Skill 的「入口开关」。误读：把精力全花在正文步骤、随手写描述。

判断4：API 适合稳定结构化操作，CUA 适合真实页面

核心判断：批量查询、结构化读取和高频写入优先用 API；页面没有接口、依赖当前登录态或需要页面证据时用 CUA。

原文依据（Skill教程 06）：「API 和 CUA 的选择：批量查询、结构化读取和高频写入优先使用 API；页面没有接口、依赖当前登录态或需要页面证据时使用 CUA。」

判断 为什么重要：选错通道会导致不稳定或浪费。误读：CUA 更智能，能用 CUA 就用 CUA。

判断5：写入前确认，写入后回查，超时先查结果

核心判断：写入类操作先展示待写字段、用户确认后执行；提交超时先按业务信息回查是否已写入，不能立即重复提交。

原文依据（Skill教程 09 本讲要点）：「写入前确认，写入后回查，超时先查结果。」

判断 为什么重要：防止重复创建需求/重复发通知。误读：超时等于失败，直接重试。

判断6：调优先从业务目标开始，v5 召回优先有明确代价

核心判断：同一个 Skill，目标不同规则取舍不同。v5 改为召回优先后 Recall 从 55.67% 升到 87.83%、FN 从 266 降到 73、F1 从 59.59% 升到 73.96%；代价是 Precision 从 64.11% 微降到 63.88%、FP 从 187 涨到 298。

原文依据（调优 05/06 页指标）：「Recall 87.83%（v4 为 55.67%）……FN 漏召回从 266 条降到 73 条……F1 73.96%（v4 为 59.59%）」「Precision 63.88%，相比 v4 的 64.11% 小幅下降……FP 298 条，误判为高潜的负样本从 187 条增加到 298 条。」

事实 为什么重要：指标提升永远要连着代价一起看。误读：只报涨的指标、隐藏涨的误判。

判断7：召回版只当第一层候选，不能当最终名单

核心判断：指标变好不等于可以直接上线最终名单；v5 适合作为第一层候选召回，后续用二次 LLM 精筛或业务规则过滤。

原文依据（调优 06/07 页）：「适合作为第一层候选召回，不适合直接作为最终业务名单。」「指标提升后还要讲清适用位置，不能把召回版当最终决策。」

判断 为什么重要：把 AI 的位置放对，比把 AI 调准更影响业务结果。误读：Recall 87% 就直接拿去触达客户。

06

关键概念拆解

Skill / SKILL.md

作者用法：教 AI 按固定流程做事的操作说明；一个 Skill 是一个文件夹，核心是 SKILL.md，可选带 scripts、references、assets。

发现（读名称+description）→ 激活（读完整 SKILL.md）→ 执行（按需读资料/跑脚本） 原文依据（Skill教程 03）：「一个 Skill 的核心是一个文件夹和一份 SKILL.md。」

不要误解成：Skill 自己能增加权限——它只能使用当前账号已拥有的能力。

Prompt / Rule / Tool / Skill 四件套

作者用法：Prompt 说明本次任务；Rule 是长期约束；Tool/MCP 连接外部系统提供能力；Skill 规定什么时候用工具、按什么步骤做、输出什么。

原文依据（Skill教程 02 对比表）。

不要误解成：四者是替代关系——它们各管一层，组合使用。本次独有的信息写 Prompt，团队要重复的写 Skill。

description（触发描述）

作者用法：既说明能做什么，也写出常见触发场景（如「当请求包含 TAPD、交付池、创建需求或登记工时时使用」）。

原文依据（Skill教程 08 SKILL.md 示例）。

不要误解成：一句越短越好的标签——它承担「路由」职能。

CUA（计算机操作能力）

作者用法：读取页面→找到控件→执行操作→验证结果→保存证据五步；失败时按步骤处理，不按固定坐标盲点，验证码和登录失效交给用户。

原文依据（Skill教程 06 步骤表）。

不要误解成：CUA 可以代替所有 API——批量、高频、结构化场景 API 更稳。

Skill 组合（一个研发场景串多个 Skill）

作者用法：处理「客户标签页面异常」：TAPD 读工单背景 → Wiki 查历史 → CLS 找日志 → 改完后 Playwright 复现截图 → GitLab 提 MR。上一步给下一步明确输入，每步保留源系统链接。

原文依据（Skill教程 04 场景段）。

不要误解成：随意串起来就行——没有明确输入接力的组合会断链。

SkillOpt 调优案例（v4 → v5）

作者用法：客户意向识别 Skill。v4 规则保守、边界客户被判「否」；v5 改召回优先：只有「已下单=是」强制排除，售后场景继续看新机/换机信号，问价格/库存/型号/到店等信号先放入候选，仍输出固定 JSON 字段。

样本 6000（正负各3000，3600/1200/1200）→ v5 规则 → test 指标 → 代价 → 适用位置 原文依据（调优 03/04 页）。

不要误解成：v5 全面优于 v4——它是「先捞候选，再精筛」流程里的第一层。

09

误解与边界

误解1：Skill 能给 AI 提权

为什么容易误解：Skill 能做到以前做不到的事，看起来像「解锁」。原文真正说了：Skill 自己不会增加 TAPD 或企业微信权限，它只能使用当前账号已经拥有的能力。原文没说：Skill 可以绕过权限体系。避免方法：无权限报错时先查账号，不是改 Skill。

误解2：指标变好 = 可以上线最终名单

为什么容易误解：单一指标叙事。原文说：指标变好不等于可以直接上线，Precision 微降、FP 增至 298，适合第一层候选召回，需二次精筛。避免方法：汇报指标时同时报收益和代价，讲清适用位置。

误解3：查询为空 / 无权限 / 接口失败都是「没有内容」

为什么容易误解：三种情况返回都很像「空」。原文说：要区分需求确实不存在、项目池选错、账号无权限和接口失败；异常要保留来源、时间范围和错误类型。避免方法：把错误类型写进 Skill 输出。

误解4：提交超时就是失败，重试就行

为什么容易误解：直觉上超时=没成功。原文说：提交超时先按业务信息回查是否已写入，不能立即重复提交；同一创建请求再次运行要提示已有记录、不重复创建。避免方法：写入路径都带「确认→执行→回查」三步。

误解5：description 是小事，正文写好就行

为什么容易误解：正文才是「内容」。原文说：description 决定什么时候加载 Skill，过窄触发不到、过宽误触发。避免方法：写清能做什么+常见触发场景（如包含「TAPD、交付池、登记工时」时使用）。

背景知识缺口

缺口1：评估指标的完整体系（现在可先不补）

本章只用了 Recall/Precision/F1/FN/FP。为什么重要：做多分类、阈值调优时还需要 ROC/AUC、混淆矩阵。下一步问题：候选池大小和阈值怎么联合定？

缺口2：二次 LLM 精筛的具体做法（原文只提了一句）

原文说「用二次 LLM 精筛或业务规则过滤候选池」，没展开。下一步问题：精筛层的提示词和指标怎么定，才不会把召回层省下的漏判又丢回去？

缺口3：Skill 的工程化分发（Plugin 化）

本章讲单机 Skill 的编写与调优；团队统一安装分发要走 Plugin（第15章讲过概念）。下一步问题：一个 Skill 稳定后怎么打包给全组？

复盘与学习报告

本章收束

• 重复、稳定、可检查的工作适合做成 Skill；description 决定什么时候加载。
