01 学习目标与阅读路径

这是一份写给"会写 C 语言、但第一次进企业项目"的同学的拆解地图。它要讲清一件事：你写下的一行代码，是怎么一路走完从需求到上线的。读完这一章，你能做到下面五件事。

1
能说出三个分支的作用：feature、release、master 分别什么时候出现、合并方向是什么、为什么代码只能改在 feature 上。
2
能背出三大阶段和流转方向：需求阶段（Feature）→ 版本阶段（Release）→ 上线阶段（Main），以及状态从"待提测"到"已提测"再到"进入上线流程"的卡点。
3
能区分灰度和正式上线：先发哪一步、合并分支的方向有什么不同、flowStatus 的 1 和 2 各代表什么。
4
能指出至少 3 个新手最常踩的坑（如直接在 release 改代码、master→release 方向搞反、灰度上线漏掉历史灰度分支）。
5
能提出 1 个追问：例如"为什么正式上线前要先把 master 合到 release，再合回 master——只做一次合并不行吗？"
阅读路径（按顺序）

先在 02 补 5 个零件 → 在 03/04 看清"这份手册在解决什么、整体怎么搭" → 在 05/06 抓住 5 条核心判断和 6 个关键概念 → 在 07 自己提问 → 在 08 闯 8 道闭环题 → 在 09/10 看边界 → 在 11 出报告。

02

零基础背景包

在拆原文前，先装 5 个最基本的零件。每个都标了"背景补充"——它帮你读懂原文，但不是任意门系统自己的设计论点，而是帮你建立"企业研发到底在干什么"的常识。

背景补充 1 · Git 分支（branch）

同一个代码仓库里，可以同时存在多条"互不干扰的代码副本"，每条叫一个分支。大家各自在一条分支上改代码，改完再合并到一起。

类比 C：分支 ≈ 同一份源码的多个副本目录，你在副本里改函数，不影响别人在主目录编译。
为什么现在需要知道：整章的核心动作（feature/release/master）全是分支名，不懂分支就读不懂"谁合并到谁"。
背景补充 2 · 环境与发布（deploy）

企业代码不会一次写完就上生产。它先发到开发环境（UAT）让开发自己联调，再发到测试环境（TEST）给测试验证，最后才发到生产环境给真实用户用。"发布"= 把代码编译打包、部署到某个环境。

类比 C：发布 ≈ 把 .c 编译成可执行文件，再 scp 到对应机器上运行；不同环境是不同的机器。
为什么现在需要知道：任意门里"发布"按钮会把应用推到不同环境的 K8s，环境错了等于发错机器。
背景补充 3 · 灰度发布（gray release）

新代码不一次给所有用户用，而是先发给一小部分用户跑一段时间。没出问题，再全量铺开。"正式"= 全量铺开给所有人。

类比 C：灰度 ≈ 先让部分机器跑新编译的程序，观察一晚上没崩，再把所有机器都换上新版本。
为什么现在需要知道：任意门把上线拆成"灰度"和"正式"两条路，方向和分支合并规则都不同。
背景补充 4 · Pod 与 K8s（容器）

服务不是直接装在物理机上，而是装进一个个"容器"里跑，K8s 是管理这些容器的平台。一个 Pod ≈ 一个正在跑的应用实例。"销毁 Pod"= 把这个实例停掉释放资源。

类比 C：K8s ≈ 一个进程管理器，Pod ≈ 一个被它 fork 出来监管的进程；销毁 Pod ≈ kill 掉这个进程。
为什么现在需要知道：任意门里"发布/重启/释放资源"全是对 K8s 上的 Pod 操作。
背景补充 5 · 配置中心（Nacos）与流水线（Tekton）

Nacos 是一个集中存放配置的网站，服务的连接地址、参数都不写在代码里，而是放在 Nacos 上，运行时去取。Tekton 是一条自动化的"构建流水线"，点一下"发布"，它自动编译、打包、推送镜像。

类比 C：Nacos ≈ 程序运行时的全局变量配置中心（改一处，所有进程读到新值）；Tekton ≈ 一条 make + scp 自动化脚本。
为什么现在需要知道：发布动作背后就是 Tekton 流水线，配置都存在 Nacos，原文反复提到这两个名字。

04

原文结构地图

判断结构类型：机制流程（一条主线从头跑到尾）。整篇是一条"需求→版本→上线"的流水线，后面 nacos/xxljob/数据库等是这条线旁边的配套工具。不要把它读成并列清单。

主线：研发完整生命周期（三大阶段） （机制流程）
  ├─ 1. 需求阶段（Feature）
  │    创建需求 + 绑定应用 → 自动拉 feature 分支 → 发布到 UAT → 联调 → "联调完成"→ 状态变"已提测"
  ├─ 2. 版本阶段（Release）
  │    创建版本 + 绑定已提测需求 → 自动拉 release 分支 → 合并 feature→release → 发到 TEST 测试环境
  │    → 测试通过后分两条路：【灰度】flowStatus=2 或 【正式上线】flowStatus=1
  ├─ 3a. 生产上线（Main·正式）
  │    合并分支：① master→release ② release→master ③ master→历史灰度分支（若有）
  │    → 构建镜像 → 推到 K8s 生产 wshoto 空间
  └─ 3b. 灰度上线（Main·灰度）
      合并分支：① master→release（单向合并）→ 构建镜像 → 推到 K8s 灰度 wshoto-gray 空间
配套工具（主线旁边的支撑） （主题簇，服务于主线）
  ├─ GitLab：源码仓库（git clone 拉代码）
  ├─ Nacos：配置中心（配置 + 服务注册）
  ├─ XXL-JOB：任务调度中心（定时任务）
  ├─ 数据库 / RocketMQ / Redis：存储与中间件
  └─ K8s（Kuboard）：容器管理平台，看应用详情
节点关系说明

主线三阶段是顺序递进（前一个没完成进不了下一个）；灰度和正式是对比关系（同一时刻只能选一条路，灰度在前、正式在后）；配套工具是支撑关系（不参与流程，但流程里每一步都要用它们）。把这三层关系分开看，就不会被一堆名词绕晕。

05

核心判断与依据

挑出 5 条最硬的判断。每条都附原文依据和类型标签。

判断 1 · 新建需求不手动建分支，由任意门自动拉 feature 分支

不要手动 git checkout 新建分支，那样不好管理；而是在任意门"新建需求"时，系统会从 master 自动拉一条以 feature 开头的开发分支。事实

在一个需求需要开发的时候，不要手动新建分支，那样不好管理……任意门会将选择的服务从 master 拉一个新的分支出来，分支的名称就是以 feature 开头的开发分支。

为什么重要：这条是整条流水线的入口，分支名和需求绑定，后续所有合并、回退都靠这个名字追溯。

判断 2 · 代码只能改在 feature 分支，严禁改 release

测试提了 bug，开发只能在 feature 分支上修，再合并到 release；严禁在 release 上直接改代码。因为版本移除需求时会默认删除 release 分支，在 release 改的代码会被带丢或带到生产。事实

严禁在 release 分支上修改代码。……这里之所以默认勾选删除 release 分支，是为了防止代码合到 release 分支，最后被带到生产上。

易误读：别以为 release 是"快车道"可以随手改——它恰恰是被严格管控、随时可能被删的那条。

判断 3 · 正式上线要双向合并：先 master→release，再 release→master

因为需求是并行开发的，master 上可能有别的需求先上线了、当前 release 里没有的代码，所以必须先把 master 合到 release（补齐），再把 release 合回 master（提交本次需求）。事实

先将 master 分支的代码合并到当前 release 分支，然后再将 release 分支的代码合并到 master……因为 master 也可能会有其他的需求先上线了。
判断 4 · 灰度只单向合并 master→release，不合回 master

灰度是把当前 release 的代码发到灰度环境先验证，所以只需把 master 上已有的新代码补进 release（避免覆盖正式环境功能），不必合回 master。推论

合并分支：将 master 分支的代码合并到当前 release 分支……发到灰度上，就不会将正式环境的功能覆盖掉。

易误读：灰度和正式的合并方向不同——灰度单向，正式双向，不能混用。

判断 5 · flowStatus 标记需求当前走的是哪条上线路

提交上线审核 flowStatus 置为 1（正式），提交灰度审核置为 2（灰度）。状态从"待提测(0)"→"已提测(1)"→"进入上线流程"，每一步都有硬卡点。事实

需求状态：待提测(flowStatus=0) → 已提测(flowStatus=1) → 进入上线流程
版本分流：正式 flowStatus=1　|　灰度 flowStatus=2
上线：提交上线审核，flowStatus → "1"……灰度：提交灰度审核，flowStatus → "2"。
06

关键概念拆解

6 个概念，环环相扣：任意门（平台）→ 拉 feature 分支 → 合并成 release 分支 → 最终进 master；灰度在 release 验证，flowStatus 标记走哪条路，nacos/k8s 是支撑设施。

① 任意门
定义微盛内部的"一站式研发效能平台"，管需求、管把服务发布到测试和生产环境。
人话一个网页，你在上面建需求、建版本、点发布、点上线，不用敲命令行。
类比 C：任意门 ≈ 一个带按钮的 IDE 插件面板，点"发布"它替你跑 make + scp + restart。
关系它是入口，feature/release 分支由它自动创建；登录后进入"应用中心→DevOps"。
任意门是需求管理，服务发布到测试环境和生产环境的平台。
不要误解成任意门 ≠ GitLab。GitLab 是源码仓库，任意门是流程平台；任意门在背后操作 GitLab 的分支。
② 三个分支：feature / release / master
定义feature-{profile}：每个需求一条，从 master 拉，开发在这里改代码；release-{profile}：每个版本一条，从 master 拉，把若干 feature 合进来去测试；master：主线，正式环境的代码来源。
人话feature 是"你一个人的草稿纸"，release 是"这一版要一起交的作业本"，master 是"已经公开出版的正式版本"。
类比 C：feature ≈ 你本地改的副本，release ≈ 小组汇总的副本，master ≈ 已发布的正式版源码。
关系feature→release→master 是合并的主方向（代码最终要进 master）；master→release 是"补齐"动作（正式/灰度上线前）。
新建需求的时候，任意门会将选择的服务从 master 拉一个新的分支出来……以 feature 开头……任意门会新建一个 release 测试分支，这个 release 分支是从 master 拉的分支。
不要误解成三条分支不是平级"随便选一个改"——只有 feature 能改代码，release/master 都靠合并进来。
③ 灰度发布（gray release）
定义正式上线前的一步：把代码先发到 wshoto-gray 灰度空间，让一部分用户先跑新代码验证。
人话先小范围试水，没问题再全量。
类比 C：灰度 ≈ 先把新编译的程序部署到几台机器上跑一晚上，观察没崩再全部替换。
关系灰度在前、正式在后；灰度只做 master→release 单向合并；提交灰度审核 flowStatus=2。
将应用发布到生产环境，wshoto-gray 空间，相当于是灰度环境。
不要误解成灰度 ≠ 正式。灰度环境（wshoto-gray）和正式环境（wshoto）是两个不同的 K8s 空间。
④ flowStatus（需求/版本的流转状态）
定义标记一个需求或版本当前走到流水线哪一步的数字标识。
人话一个状态码，告诉系统"这单子现在卡在哪"。
需求：待提测(0) → 已提测(1) → 进入上线流程
版本上线分流：正式审核 flowStatus=1　|　灰度审核 flowStatus=2
关系需求没"已提测"就不能被版本绑定；版本没合并/没发布就不能提交上线审核。
创建需求 → 待提测(flowStatus=0) → … → 已提测(flowStatus=1) → 上线/灰度 → 进入上线流程。
不要误解成需求状态里的"1"（已提测）和版本分流里的"1"（正式上线）含义不同——前者是需求层、后者是版本层，看上下文。
⑤ Nacos（配置中心 + 服务注册）
定义阿里巴巴开源的服务发现与配置管理平台。微盛用它统一存各服务的配置（数据库地址、redis 地址、参数），并登记每个服务实例的注册信息。
人话一个集中改配置的网站，改一处所有服务都读到新值；同时是"有哪些服务在跑"的花名册。
类比 C：Nacos ≈ 程序运行时的全局变量配置中心 + 已注册函数指针表；改配置不用重新编译，运行时生效。
关系可在任意门"应用中心→Nacos"里直接修改测试/生产配置；redis 连接信息也存在 Nacos 的 redis-info.yaml。
可以在任意门上修改、查看 nacos 配置，以及查看服务注册。
不要误解成Nacos ≠ 数据库。它存的是"配置"（小量、键值型），不是业务数据。
⑥ K8s（Kubernetes / Kuboard）
定义容器编排平台，把服务装进容器（Pod）跑起来、自动管理副本数。微盛用 Kuboard 作为 K8s 的可视化管理界面。
人话一个管"程序在哪里跑、跑几个、挂了重启"的大管家。
类比 C：K8s ≈ 一个进程管理器（supervisor），Pod ≈ 它监管的一个进程；任意门"发布"就是让 K8s 拉起新 Pod。
关系任意门所有"发布/重启/释放资源"操作最终都是对 K8s 的 Pod 操作；测试环境在 wshoto 命名空间，灰度在 wshoto-gray。
我们的服务都是容器部署的，在任意门上发布的应用都是发布到 k8s 上了……测试环境的应用都在 wshoto 命名空间。
不要误解成K8s ≠ 虚拟机。Pod 是临时的、可被随时销毁重建的，所以"释放资源/销毁 Pod"很常见、不是删服务。
07

苏格拉底式阅读关卡

不直接给答案，自己想。参考答案在每题下方，但请先停 30 秒再展开。

Q1 · 入门原文说"不要手动新建分支，那样不好管理"，这是事实、判断，还是推论？
这是判断——是任意门团队对"该怎么管分支"的主张。背后的事实依据是"任意门会自动从 master 拉 feature 分支"。判断建立在事实之上，但"手动不好管理"本身是观点。
提示：区分"系统怎么做"（事实）和"该怎么做"（判断）。
Q2 · 入门"feature 分支从 master 拉、release 分支也从 master 拉"——这两条都是事实吗？
是事实。原文明确：新建需求时从 master 拉 feature；新建版本时任意门新建 release 测试分支，"这个 release 分支是从 master 拉的"。注意 release 不是从 feature 拉的，而是独立的，feature 是被"合并进"release 的。
Q3 · 进阶为什么严禁在 release 分支上改代码？如果偏要在 release 上改，会发生什么？
因为版本移除需求时会默认勾选删除 release 分支，目的是"防止代码合到 release 分支，最后被带到生产上"。你在 release 上改的代码，可能随删除一起丢失，也可能漏过审核被带进生产——两种都很危险。
提示：回到 05 判断 2 的原文依据。
Q4 · 进阶正式上线前为什么要"先 master→release，再 release→master"？只做一次合并不行吗？
因为需求是并行开发的，master 上可能已经有别的需求先上线了，而当前 release 里没有这些代码。只做 release→master，会把"当前版本没包含的新功能"用旧版覆盖掉（回退正式环境）。必须先 master→release 补齐，再 release→master 提交。
Q5 · 进阶灰度上线只做 master→release 单向合并，为什么不合回 master？
灰度只是"先验证一下"，代码还没正式生效，不应污染 master。合回 master 等于把"还没验证通过的代码"定为正式基准。等灰度没问题，走正式上线流程时，才会通过 release→master 把代码并进 master。
Q6 · 深度正式上线如果存在"历史灰度分支"，为什么还要把 master 合到历史灰度分支？
历史灰度分支上还有正在灰度的旧版本用户在跑。如果不把 master 的最新代码合过去，那条历史灰度分支会和正式环境越走越远，将来它转正式或回退时就会产生冲突。这一步是保持分支不偏离的补救动作。
提示：注意 04 结构地图里正式上线的第三步合并。
Q7 · 深度需求状态从"待提测"到"已提测"的卡点是什么？为什么不能跳过？
卡点是联调完成（在任意门点"联调完成"按钮，并发布到开发环境验证过）。跳过它，需求就不会出现在版本的"已提测"列表里，测试就搜不到、没法绑进版本。整条流水线的第一道闸就在这里。

误解与边界

误解 1 · "release 是测试分支，可以直接在上面改代码"
为什么容易误解C 写多了，习惯在"当前在用的那份源码"上直接改。
原文真正说了严禁在 release 分支上修改代码；移除需求时默认删除 release 分支。
原文没有说"release 方便随手改"——反而把它定义为会被随时删除的分支。
如何避免所有改动回到 feature 分支，再合并进 release。
误解 2 · "正式上线合并就是 release→master 一次就够"
为什么容易误解直觉上"我的代码要进 master，那就合过去"。
原文真正说了先 master→release（补齐别人先上线的代码），再 release→master（提交本次需求），两步缺一不可。
原文没有说"单向合并就行"——漏掉第一步会把正式环境的新功能用旧代码覆盖。
如何避免正式上线永远做双向合并；若存在历史灰度分支，还要 master→历史灰度分支。
误解 3 · "灰度和正式差不多，发哪个环境都行"
为什么容易误解都叫"上线"，看起来只是按钮不同。
原文真正说了灰度发 wshoto-gray 空间、单向合并、不合回 master；正式发 wshoto 空间、双向合并、合回 master。两条路规则完全不同。
如何避免灰度在前（先小范围验证），正式在后（验证通过才全量）；二者是顺序关系不是二选一。
误解 4 · "Nacos 是个数据库，能存业务数据"
为什么容易误解看到 nacos 里能"查看/修改"东西，以为是数据存储。
原文真正说了Nacos 用于"修改、查看配置"和"查看服务注册"，存的是 yaml 配置（如 redis-info.yaml），不是业务数据。
如何避免业务数据在 PostgreSQL（数据库），Nacos 只管配置和服务发现。
误解 5 · "销毁 Pod = 把服务删了/下线了"
为什么容易误解"销毁"听起来像把程序卸载了。
原文真正说了销毁 Pod 是"回收 K8s Pod 资源"，比如联调完成后销毁开发环境的 Pod 释放资源；正式服务随时可以重新发布拉起来。
如何避免把 Pod 理解成"可随时重建的进程实例"，销毁 Pod ≈ kill 进程，不是卸载服务。

背景知识缺口

要彻底吃透这一章，建议补这 4 个背景。现在不补也行，遇到不懂的再回头看。

缺口 1 · Git 合并（merge）与冲突解决

原文反复说"合并分支"，但没讲合并本身。建议补：git merge 的三方合并、fast-forward、冲突手动解决。类比 C：合并 ≈ 把两个副本目录的 diff 人工对齐应用到主目录。为什么重要：合并方向是整章核心，不懂 merge 就不懂"为什么先合谁"。

缺口 2 · CI/CD 与 Tekton 流水线

原文的"发布"背后是 Tekton Pipeline 自动构建镜像。建议补：什么是 CI（持续集成）、CD（持续部署）、镜像（image）、流水线（pipeline）。类比 C：Tekton ≈ 一条自动跑 make && scp && restart 的脚本链。下一步追问：为什么不能本地 make 完手动传上去？自动化带来什么保障？

缺口 3 · 容器与 K8s 基础

建议补：什么是容器（Docker）、Pod、Deployment、命名空间（namespace）、副本数。原文里"工作负载 867、容器组 4257、wshoto 命名空间"都基于这套概念。为什么重要：理解了 Pod 是临时的，才理解"销毁/重启 Pod"为什么是常规操作。

缺口 4 · 微服务与中间件

建议补：什么是微服务架构、为什么有 nacos（服务注册发现）、rocketmq（消息队列）、redis（缓存）、xxljob（定时任务）这些中间件各自解决什么问题。为什么重要：原文最后几节是中间件速查，懂了它们的定位，才知道一个需求可能同时改 nacos 配置、加 xxljob 任务、发 mq 消息。

可以暂时不补的

GitLab CI 的 .gitlab-ci.yml 细节、Kuboard 的具体操作按钮、PostgreSQL 的 SQL 语法——这些是工具操作层，不影响理解研发流程的整体骨架。
