01 学习目标与阅读路径

这是一份写给"会写代码、但第一天踏进微盛前端"的同学的导航地图。它要讲清一件事：你拿到一个需求，应该进哪个仓库、切哪个分支、走哪条发布流程。读完这一章，你能做到下面五件事。

1
能分清 5 个工程仓库：知道 qv-admin / qv-admin-h5 / ws-wx-app / qv-admin-h5-customize / qv-admin-customize 分别是什么端、用在哪、对应仓库地址，以及"标品"和"定开"的分界。
2
能讲清标品 vs 定开 vs 私有化：三种开发模式各自的特点、对应工程是谁、为什么"开发无需关注 SAAS 部分，只管定开"。
3
能记住分支命名和切分规则：标品 feature-[tapdId]-时间、定开 customer/[项目名]/dev|release、私有化从基线分支切（baseline-2512 / release-2512）；以及禁止合并 release 到 feature 这条红线。
4
能独立完成本地开发流程：登录测试环境拿 token → 改 .env.development 的 VUE_APP_BASE_URL 和 VUE_APP_DEBUG_TOKEN → npm run dev，以及这条流程为什么不适用微信端。
5
能区分 3 种发布方式：标品每周二晚 8 点测试统一发；SAAS+定制发租户 id+分支给居易；私有化自行 jenkins 打包发运维——以及谁负责合代码、谁负责构建。
阅读路径（按顺序）

先在 02 装 6 个零件（SPA / 定开 / 基线 / 特性环境 / PR / jenkins）→ 在 03/04 看清"这份手册在解决什么、整体怎么搭" → 在 05/06 抓住 5 条核心判断和 5 个关键概念 → 在 07 自己提问 → 在 08 闯 8 道闭环题 → 在 09/10 看边界 → 在 11 出报告。

02

零基础背景包

在拆原文前，先装 6 个最基本的零件。每个都标了"背景补充"——它帮你读懂原文，但不是微盛自己的设计论点，而是帮你建立"企业前端到底在干什么"的常识。

背景补充 1 · SPA（单页应用）

微盛前端工程都是 Vue 写的 SPA（Single Page Application）：整个网站其实只有一个 HTML 页面，切换功能时不再从服务器拉整个新页面，而是 JS 在前台动态替换内容，数据通过 ajax 异步加载。所以本地开发要解决"前台页面在跑、但要用测试环境的接口和数据"——这正是 token 注入的由来。

类比：SPA ≈ 一个一直在前台运行的应用程序，HTML 是它的"壳"，数据是它运行时通过网络拿到的"输入"。
为什么现在需要知道：原文"修改 VUE_APP_DEBUG_TOKEN 为 token 值"就是给这个 SPA 注入一个登录态，让它能调测试环境的接口。
背景补充 2 · 定开（定制开发）

"标品"是面向所有客户的标准产品；"定开"是某个客户付了钱，要求在标品基础上为它单独做的功能。微盛把这两类代码放在不同的仓库里，标品改标品的、定开改定开的，互不污染。一个客户买到的产品 = 标品 + 它自己的定开。

类比：标品 ≈ 量产车型，定开 ≈ 给某个客户单独改装的部分（不改原厂量产车，而是在改装厂加装）。
为什么现在需要知道：原文反复强调"开发人员无需关注 SAAS 部分，专注于定开部分"——你接到定开需求，只动定开仓库就行。
背景补充 3 · 基线（baseline）

私有化客户不买 SAAS 服务、而是把整个系统部署到自己服务器上。但它不能"随时拷一份现在的 SAAS"——因为 SAAS 在持续迭代。所以微盛会在某些时间点（比如 2025 年 12 月）从 SAAS 主干签出一个版本，这就是"基线"（2512 基线）。私有化客户基于某个固定基线部署，基线只更新不重做。

类比：基线 ≈ 一份带版本号的快照（snapshot），客户买的是"2025 年 12 月这一版"。
为什么现在需要知道：私有化开发的入口是先确认"客户用哪个基线"，再从对应的基线分支切。
背景补充 4 · 特性环境（release-*）

"特性环境"不是命名规范，而是一种用需求发布时间做测试环境标识的做法。多个需求并行开发、不同时间上线，测试环境就会同时存在多个特性分支（如 release-v2026071420260721 表示 2026 年 7 月 14 日灰度、7 月 21 日正式）。它们互相独立，互不干扰。

类比：特性环境 ≈ 给每个"批次的需求"分一个独立的测试房间，房间门牌号就是这批需求的上线日期。
为什么现在需要知道：标品开发提交 PR 时，目标分支就是这个 release-* 分支，由测试告诉你具体填哪个。
背景补充 5 · PR / MR（合并请求）

PR（Pull Request，GitLab 里常叫 MR Merge Request）= "请把我这条分支的代码合并到目标分支"的申请。它不是直接 push，而是发起一个由别人审核的合并流程：审核通过才真正合代码。微盛规定 PR 由居易或阿遥审核。

类比：PR ≈ 提交一份代码变更的"申请单"，主管签字（审核通过）后才生效；不是你自己拍板。
为什么现在需要知道：标品的测试/上线阶段都靠 PR 推进；冲突千万别自己在 web 端解（会导致反向合并）。
背景补充 6 · Jenkins（持续集成工具）

Jenkins 是一个自动化的"打包构建服务器"。配置好任务后，点一下（或推个 commit 触发），它就自动拉代码、npm install、npm build、把产物部署出去。微盛私有化由开发自己创建 jenkins 任务打包，SAAS+定制由居易统一建 jenkins 任务发布。

类比：Jenkins ≈ 一台会按配方自动跑 npm 脚本的服务器，输出可部署的产物。
为什么现在需要知道：原文 7.1.2、7.1.3 的发布都靠 jenkins，理解它你就懂"为什么定开要给居易发分支"。

05

核心判断与依据

挑出 5 条最硬的判断。每条都附原文依据和类型标签。

判断 1 · 5 个工程严格区分"标品"和"定开"，且代码隔离

2.1/2.2/2.3 是标品工程，2.4/2.5 是定开工程——它们是不同的代码仓库。SAAS+定制模式下，开发人员"无需关注 SAAS 部分，专注于定开部分的实现"，意味着你接到一个定开需求，只动定开仓库，标品代码完全不用碰。事实

上述5个工程，2.1，2.2，2.3为标品工程，2.4，2.5为定开工程……开发人员无需关注SAAS部分，专注于定开部分的实现。定开部分代码工程根据设备终端不同分为移动端定开（2.4）和PC端定开（2.5）。

为什么重要：新人最容易犯的错就是"我想改这个功能，去标品仓库改吧"——错。要做定制，去定开仓库。

判断 2 · 基线是 SAAS 在某时间点的快照，不是实时同步

基线不是"SAAS 的最新代码"，而是"在指定时间点从 SAAS 主干派生出的分支"。比如 2512 基线就是 2025 年 12 月签出的那一版。私有化客户基于某个固定基线部署，同步基线代码时也只能同步当前基线的最新代码，不能任意挑某个时间点。事实

基线是指在指定的时间点从标品SAAS派生出的分支（比如，2025年12月从SAAS主干上签出了一个版本，那么就是2512基线）。

为什么重要：把基线当 SAAS 主干用、随便同步代码，会让客户服务器上的版本错乱——这是大坑。

判断 3 · 严禁把 release-* 合并到 feature / hotfix

release-* 是特性环境分支（可能含多个需求），如果把它合回自己的 feature 分支，会把别人的代码、未上线的需求都污染进你的开发分支。这条是手册里写明的红线。事实

切记不可将远程或者本地的release-*分支合并到自己的feature，hotfix 分支。

易误读：方向是 release → feature 被禁，反过来 feature → release 是允许的（这正是上线合并的正方向）。

判断 4 · PR 冲突不能在 web 端自己解决

GitLab 的 web 端冲突解决工具会"反向操作"——比如你要 A 合到 B，它会变成 B 合到 A，把目标分支弄乱。所以遇到 PR 冲突，必须联系居易或阿遥处理，不要自己点 WebIDE。事实

提交的PR存在冲突时，切记不要使用web端的工具自行解决冲突（会导致反向操作，比如：pr是A合到B, 该方式会B合到A）……联系居易或者阿遥处理。
判断 5 · 标品分支从 master 切；定开从 master-vue3 切；私有化从基线分支切

三种开发模式的切分起点不同：标品从 master 切 feature；定开（Vue3 版本）从 master-vue3 切 customer 分支；私有化从标品仓库的 baseline-2512（基线部分）或定开仓库的 release-2512（定开部分）切 customer 分支。起点错了，整个分支就废了。事实

标品：master → feature-[tapdId]-时间
定开：master-vue3 → customer/[项目名]/dev|release
私有化：baseline-2512 / release-2512 → customer/[项目名]/xx
标品需求开发：从master分支切出新的feature分支……SAAS+定制：从master-vue3（Vue3版本）中切出新的定开分支……私有化：从标品仓库的baseline-2512分支上切出项目的分支。
06

关键概念拆解

5 个核心概念：5 个工程仓库（标品3+定开2）→ 3 种开发模式（决定走哪条分支规则）→ 基线（私有化的起点）→ 特性环境（标品测试的房间号）→ 分支命名规范（每个模式的命名格式）。把这 5 个串起来，你就懂整篇手册。

① 5 个工程仓库
用途微盛前端代码按"端 + 标品/定开"分成 5 个独立仓库，每个仓库一个 git 地址、一套目录结构。
编号工程类型仓库地址
2.1PC管理端（企微管家-管理端）标品gitlab.oa.com/root/qv-admin
2.2移动端工作台（员工端）标品gitlab.oa.com/root/qv-admin-h5
2.3微信端（客户端，营销活动）标品gitlab.oa.com/wshoto-fe/ws-wx-app
2.4移动端定开定开gitlab.oa.com/wshoto-fe/qv-admin-h5-customize
2.5PC端定开定开gitlab.oa.com/wshoto-fe/qv-admin-customize
人话标品 = 给所有客户用的标准产品；定开 = 给某个客户单独定做的部分。两者物理隔离在不同仓库，互不污染。
类比：标品仓库 ≈ 量产车的原图纸；定开仓库 ≈ 给特定客户改装的图纸副本；两张图纸分开存。
关系客户买到的产品 = 标品代码（2.1/2.2/2.3）+ 它自己的定开代码（2.4 或 2.5，视终端而定）。
不要误解成"定开就是改标品"——不是。定开是完全独立的仓库，标品代码你看都看不到改动入口。
② 3 种开发模式
定义决定你这次需求走哪条规则链：标品SAAS、SAAS+定制、私有化。
模式代码工程特点
3.1 标品SAAS2.1/2.2/2.3标准产品每周迭代，由标品SAAS产品经理提需求
3.2 SAAS+定制标品 + 2.4/2.5SAAS基础上做定制；开发只管定开部分，无需关注SAAS
3.3 私有化基线 + 2.4/2.5SAAS某时间点快照（基线）部署到客户私有服务器；开发只管定开
人话标品 = 给所有人用的版本；SAAS+定制 = 客户用了 SAAS 又加点私货；私有化 = 客户整套搬回家自己装。
关系开发模式决定了你切哪种分支、走哪种发布（详见判断 5 和概念⑤）。
不要误解成不管什么模式都要改 SAAS 代码——后两种模式明确说"开发无需关注 SAAS 部分"。
③ 基线（baseline）
定义从标品 SAAS 主干在某个时间点签出的快照分支，命名形如 baseline-2512（2025年12月）、release-2512（定开仓库对应的基线分支）。
人话SAAS 的某个"定版"，给私有化客户用，避免客户代码跟着 SAAS 每周变。
类比：基线 ≈ 给某个时间点的 SAAS 拍了张照片，私有化客户买的就是这张照片。
关系私有化的"基线部分"从标品仓库的 baseline-2512 切；"定开部分"从定开仓库的 release-2512 切。基线部分不允许做任何定制改动，仅支持同步基线代码。
私有化基线部分的分支不允许做任何定制改动，仅支持同步基线代码。
不要误解成基线不是 SAAS 主干，不能随便拿最新 SAAS 同步——只能同步当前基线的最新代码，且依赖后端的话要前后端同时发。
④ 特性环境（release-*）
定义标品的测试环境分支，用需求的灰度/正式发布时间做标识，如 release-v2026071420260721 = 2026年7月14日灰度、7月21日正式。
人话给"一批要在某天上线的需求"分一个独立测试房间，房间门牌号就是上线日期。
类比：特性环境 ≈ 酒店的临时包间，按"几点退房"编号；不同需求各自一个包间，互不打扰。
关系标品开发完成后，提交 PR 的目标分支就是这个 release-* 分支（由测试告诉你具体填哪个）。多个特性环境会同时存在。
为了统一发布内容，故使用了需求的灰度/生产发布时间作为测试环境的特性标识（如release-v2026071420260721）。
不要误解成特性环境 ≠ 生产环境，也 ≠ master。它是测试用的、临时的、按需求批次划分的。
⑤ 分支命名规则
定义每种开发模式有自己的分支命名格式，必须按规范起名。
场景格式说明 / 例子
标品 · 需求feature-[tapdId]-时间feature-1214757-20260626（tapdId=TAPD需求id）
标品 · bughotfix-[tapdId]-时间hotfix-1214757-20260626（线上bug从master切）
定开 · 需求customer/[项目名]/dev|releasecustomer/{客户英文名}/dev 或 release，视环境而定
定开 · bug—无特殊要求
环境分支master / release-gray / release-* / baseline-*生产/灰度/测试/基线 各对应一类分支
关系每个项目的分支还要登记到《ka前端项目管理》文档，不能私下乱建。
需求开发：feature-[tapdId]-时间……bug修复：hotfix-[tapdId]-时间……customer/[项目名称]/release|dev。
不要误解成分支名不是"我想叫啥叫啥"——名字里藏着 TAPD id，是为了能从分支追溯回需求。

苏格拉底式阅读关卡

不直接给答案，自己想。参考答案在每题下方，但请先停 30 秒再展开。

Q1 · 入门为什么定开和标品要分成两个独立仓库，而不是放在同一个仓库的不同分支里？
因为定开代码是某个客户独有的，标品是所有客户共享的。如果放同一个仓库用分支区分，风险是：合并时容易把定制代码漏进标品主干（影响所有客户）、或者标品的迭代破坏某个客户的定制。物理隔离仓库是最硬的隔离——从根本上杜绝互相污染。这也是为什么原文反复说"开发无需关注 SAAS 部分"。
提示：从"隔离边界"和"事故影响面"两个角度想。
Q2 · 入门基线为什么不直接用 SAAS 主干，而要在某个时间点单独签出一个版本？
因为 SAAS 主干每周都在迭代（标品每周二晚发版），代码一直在变。私有化客户把系统部署到自己服务器上，要求稳定——它不能每周都跟着变，更不能把"还没验证过的 SAAS 最新代码"直接推到客户机器上。所以微盛在固定时间点（如 12 月）签出基线，给私有化客户一个"经过验证的、稳定冻结的版本"。客户基于这个基线长期维护。
Q3 · 进阶为什么 PR 有冲突时，不能自己在 GitLab web 端用 WebIDE 解决？
因为 GitLab web 端解决冲突的工具会反向操作——你的本意是"A 合到 B"，但 web 工具会变成"B 合到 A"，把目标分支的代码搞乱。原文明确警告这一点。正确做法是联系居易或阿遥，他们在本地用正确方向解决冲突后再合，避免反向污染。这条规则的潜台词是：分支合并方向非常重要，方向错了事故面很大。
提示：回到「05 判断 4」的原文依据。
Q4 · 进阶为什么标品要从 master 切 feature，定开却要从 master-vue3 切？这背后是什么历史？
这是技术栈升级留下的历史遗留。2025 年 10 月以前标品是 Vue2 版本（master），10 月以后升级到 Vue3（master-vue3）。但 SAAS+定制的项目混有两种版本：老项目在 Vue2 上维护（从 master 切），新项目在 Vue3 上（从 master-vue3 切）。原文明确"2025年10月以后的标品升级为vue3……定制部分需要从该分支上切出"——所以现在做定开默认从 master-vue3 切。
Q5 · 进阶本地开发要改 .env.development 注入 token，为什么微信端不适用这套流程？
因为微信端（2.3 ws-wx-app）面向 C 端客户，没有登录鉴权——它本来就是在微信里直接打开的营销活动页，不需要登录。既然不需要登录，就没有"拿登录 token"这一步。所以原文说"微信端调试时需要自行 mock 页面上的业务参数即可调试"——你直接在代码或 url 里塞入业务需要的参数（如某个活动 id、用户 openid），就能调起来。
Q6 · 深度私有化发布时，"如果同步代码依赖后端服务，则要前后端同时发布"——为什么？
因为同步过来的代码可能调用了新版本后端的接口（参数、字段、路由变了）。如果前端发了、后端没发，前端调的就是旧后端，参数对不上、直接报错或数据错乱。所以私有化同步基线代码时必须前后端版本一致——这是为了避免"前端跑在新的、后端跑在旧的"这种不兼容状态。SAAS 模式没这条强调，是因为 SAAS 后端版本由平台统一管控。
提示：从"前后端接口契约"角度想。
Q7 · 深度为什么"私有化基线部分的分支不允许做任何定制改动，仅支持同步基线代码"？
因为基线部分对私有化客户来说就是"它的 SAAS"。如果你在基线分支上直接改代码，相当于改了客户部署的标品——这会让这个客户的"标品"和其他客户的基线分叉、再也回不去标准版，将来同步基线代码时会冲突或丢失定制。定制只能放在定开仓库的 release-2512 切出来的定开分支里，基线分支永远保持"纯 SAAS 快照"的干净状态。

误解与边界

误解 1 · "做定制需求，要去标品仓库改 SAAS 代码"
为什么容易误解直觉上"这个功能在 PC管理端，那就去 qv-admin 改"。
原文真正说了定制有独立仓库（2.4 qv-admin-h5-customize、2.5 qv-admin-customize）；"开发人员无需关注SAAS部分，专注于定开部分的实现"。
原文没有说"定制就是在标品上加几行代码"——标品和定开是物理隔离的独立仓库。
如何避免接到需求先问"标品还是定开"，定开就去 2.4 或 2.5，绝不碰标品仓库。
误解 2 · "feature 分支可以合并最新的 release-*，保持代码最新"
为什么容易误解以为"代码越新越好"，习惯把上游分支合到自己的分支。
原文真正说了切记不可将 release-* 合并到 feature/hotfix；如开发周期较长，是把 master 合并到 feature，不是 release。
原文没有说"定期同步 release"——release 是特性环境，含别人未上线的需求，合进来会污染你。
如何避免想同步最新代码，永远合 master，不碰 release-*。
误解 3 · "基线可以随便同步 SAAS 最新代码，或者回到任意历史版本"
为什么容易误解把基线当成 SAAS 的别名，以为想同步什么同步什么。
原文真正说了基线是某时间点的快照；同步代码仅支持同步当前基线的最新代码，不支持同步当前基线的某一时间点的代码。
原文没有说"基线 = SAAS 主干最新版"——基线是冻结的、带版本号的，不能跨基线、也不能挑历史时刻。
如何避免私有化同步前先确认客户用的是哪个基线（如 2512），只能拉这个基线分支的最新代码。
误解 4 · "本地开发流程对所有端都适用，微信端也走 token 注入"
为什么容易误解看到"标品本地开发流程"，以为 PC/移动/微信三端通用。
原文真正说了这套流程仅适用于需要登录鉴权的 PC 端；微信端面向客户、无需登录鉴权，调试时 mock 业务参数即可。
原文没有说"微信端拿 token"——它根本不要登录，没有 token 这一步。
如何避免做微信端调试，直接在 url 或代码里塞业务参数（活动 id 等），不走 .env token 流程。
误解 5 · "PR 冲突自己在 GitLab web 端解掉就行，反正工具自动处理"
为什么容易误解GitLab 提供了 WebIDE 解决冲突的按钮，看起来很方便。
原文真正说了web 端工具会导致反向操作（A 合 B 变成 B 合 A）；正确做法是联系居易或阿遥处理。
原文没有说"web 端工具可以用"——反而把它列为禁忌。
如何避免遇到 PR 冲突，第一反应是 @居易 或 @阿遥，绝不自己点 WebIDE。

背景知识缺口

要彻底吃透这一章，建议补这 3 个背景。现在不补也行，遇到不懂的再回头看。

缺口 1 · Vue3 工程结构与环境变量

原文反复提 .env.development、VUE_APP_BASE_URL、VUE_APP_DEBUG_TOKEN、master-vue3，但没讲 Vue 工程本身。建议补：Vue CLI / Vite 的工程目录、.env 文件的多环境机制（.env.development / .env.production）、VUE_APP_ 前缀的环境变量怎么读。为什么重要：本地开发流程就是改 .env，不懂环境变量就改不明白。

缺口 2 · GitLab PR / MR 流程

原文反复说"提交 PR、目标分支、审核通过"，但没讲 PR 本身。建议补：GitLab 里怎么发 Merge Request、source/target 分支怎么选、PR 状态（open/merged/conflicts）、WebIDE 解决冲突为什么有反向操作的问题。下一步追问：为什么 GitLab web 工具会"反向合并"？是工具 bug 还是设计如此？

缺口 3 · Jenkins 与持续部署

原文 7.1.2、7.1.3 都靠 jenkins，但没讲 jenkins 怎么用。建议补：jenkins job 怎么建、构建触发器、构建产物（dist）怎么部署、私有化"打包后发运维"具体发的是什么。为什么重要：理解了 jenkins，才懂"为什么定开要把分支给居易、私有化要自建任务"。

可以暂时不补的

企微管家产品的具体业务功能（每个菜单是干啥的）、Vue3 的 Composition API 语法、jenkinsfile 的 DSL 细节——这些是业务和工具操作层，不影响你理解"工程怎么组织、流程怎么走"。
