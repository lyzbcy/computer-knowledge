wshoto-framework 脚手架

基于《wshoto-framework 3.0 脚手架开发者手册》（2026-07-19）深度拆解 · 受众：Java 后端开发管培生

01 学习目标与阅读路径

这是公司所有 Java 微服务共用的二方包框架，掌握它就能站在巨人的肩膀上做业务。学完你应该能做到：

1
背出技术核心版本——Java 17、Spring Boot 3.4.0、Spring Cloud 2024.0.0、Spring Cloud Alibaba 2023.0.3.2、MyBatis-Plus 3.5.12、ShardingSphere 5.5.1、RocketMQ 5.3.1、Redisson 3.16.8。
2
说清三层依赖关系——wshoto-parent 是底；wshoto-framework-parent 是 BOM（只统一版本不传递依赖）；各业务子模块按需在 <dependencies> 中显式引入 starter。
3
记住新服务接入的最小组合——common + config-nacos + discovery-nacos + log + trace + web + monitor 是必须的；按需加 redis/stream/sharding 等。不要「省事」全引入。
4
理解「占位 starter 陷阱」——config-core-starter、discovery-core-starter 源码只有 package-info.java，引入它们不会获得任何能力，必须用对应的 nacos/local 实现包。
5
掌握泳道（lane）机制——租户映射到 MASTER/GRAY 发布环境，HTTP 入口写入 ContextHolder，Feign 负载均衡、MQ group/tag、延时消息 header 都消费这个上下文。

阅读路径：补 Spring Boot starter 机制 → 三层依赖关系 → 新服务接入步骤 → 各 starter 能力地图 → 踩坑实战 → 复盘。

02 零基础背景包

背景补充 1：Spring Boot starter 机制

背景补充

starter 是 Spring Boot 的「依赖打包+自动配置」约定：引入一个 starter，相当于一次性把一组相关 jar 和自动配置类加到 classpath，开箱即用。比如引入 redis-boot-starter，Redisson 客户端和默认 Bean 都自动建好。

为什么读本文需要它：wshoto-framework 把每个能力（配置、发现、日志、Redis、MQ）都封装成独立 starter，业务服务按需引入。

背景补充 2：BOM（Bill of Materials）

背景补充

BOM 是 Maven 的「版本清单 POM」。用 <dependencyManagement> + type=pom scope=import 引入后，它只统一二方包版本，不会把 jar 自动加到 classpath。业务模块还是要自己写 <dependencies>。

为什么读本文需要它：手册反复强调「不要仅依赖 wshoto-framework-parent」，因为它是 BOM，引入它不会获得任何 starter。

背景补充 3：Nacos 配置中心 + 注册中心

背景补充

Nacos 同时承担两个角色：①配置中心——按 namespace/group/dataId 三元组存配置文件，应用启动时拉取并支持动态刷新；②注册中心——服务实例启动时把自己注册进去，调用方通过服务名查实例列表。

为什么读本文需要它：config-nacos-boot-starter 和 discovery-nacos-boot-starter 是公司服务的两个「必须引入」包。

背景补充 4：TTL（TransmittableThreadLocal）

背景补充

阿里开源的线程池上下文传递组件。普通 ThreadLocal 在线程池场景下子线程拿不到父线程的值，TTL 解决了这个问题，让 traceId、tenantId、laneId 等上下文跨线程池传递。

为什么读本文需要它：ContextHolder 用 TTL 保存上下文，线程池必须用 TTL 包装（TtlExecutors.getTtlExecutor）。

03 原文问题定位

表面在讲什么？

30+ 个 starter 模块的能力说明：config 家族（core/local/nacos/extension）、discovery 家族、lane 泳道、trace、log、web、monitor、message、stream、delay、event、redis、extension、registry、orm、sharding-jdbc、report、scheduler、apidoc、encryptor、test。

深层在回答什么问题？

「上百个 Java 微服务，怎么把配置/发现/日志/链路/Redis/MQ/分片/调度这些基础设施统一管起来，业务只写业务代码？」

答案是「模块化二方包 + 按需引入 starter + 框架统一管上下文」：原文：每个功能模块独立封装为二方包，业务服务可以按需引入相关依赖。

作者为什么要写这篇？

这是开发者手册，目标是让新服务快速接入、让老服务知道每个 starter 的能力边界和排障方法。手册特别强调「源码事实 vs 参考手册差异」（比如 config-local 的 watch-interval 配置键根本不存在，固定 3 秒）。

只记一个问题

「新服务怎么接入框架？每个 starter 给我什么能力？」——继承 wshoto-parent → 导入 framework BOM → 按需引 starter → 配 Nacos → 框架统一管上下文透传。

04 原文结构地图

原文结构类型：能力目录 + 模块卡片（每个 starter 一个固定模板：基本信息/依赖与核心类/作用与实现/业务使用示例/如何确认已生效/边界风险排障）

核心：框架 = 公共包 + 配置家族 + 发现家族 + 业务能力 starter 集合
基础层：wshoto-framework-common
Result/Response/BaseException/ContextHolder/注解/工具类。所有 starter 的依赖上限。
配置家族（config-*）
core（占位）→ nacos（Spring Cloud Alibaba）/ local（3秒文件刷新）/ extension-core（SPI）/ extension-local/nacos（动态规则）
发现家族（discovery-*）
core（占位）→ nacos（注册+泳道负载均衡）/ local（静态服务列表）
上下文与可观测（lane/trace/log/monitor/web）
lane（租户→泳道）、trace（traceId 透传）、log（@WebLog+TTL MDC）、monitor（Prometheus 指标）、web（XSS/签名/压缩）
消息与调度（message/stream/delay/event/scheduler）
message-core（模型）→ stream（RocketMQ 生产消费）/ delay（延时消息）/ event（埋点）/ scheduler（XXL-JOB）
数据层（orm/sharding-jdbc/report/redis）
orm（MyBatis-Plus 通用）、sharding-jdbc（分库分表+影子库）、report（多数据源）、redis（Redisson+两层配置）
扩展与治理（extension/registry/apidoc/encryptor/test）
extension（业务扩展点）、registry（Feign 白名单）、apidoc（OpenAPI）、encryptor（ENC 解密）、test（TestNG+Mock）
节点关系说明：模块之间是依赖与组合关系：common 是所有 starter 的根；config-extension-core 是 lane/registry/extension/sharding 的 SPI 底座；stream 依赖 message-core 和 lane；sharding 依赖 config-extension。业务服务按需「搭积木」组合这些 starter。

05 核心判断与依据

判断1：三层依赖关系不能混淆

原文依据：原文 2.2：wshoto-framework-parent 和业务服务根 POM 都通过 <parent> 继承 wshoto-parent；业务服务在 <dependencyManagement> 中以 type=pom、scope=import 导入 wshoto-framework-parent；它只统一二方包版本，不会把 common 或任何 starter 自动加入 classpath

层角色能做/不能做
wshoto-parent底座父 POMJDK/Spring Boot BOM/插件基线
framework-parentBOM（版本清单）统一二方包版本，不传递依赖
业务子模块实际依赖方按职责显式 <dependencies> 引入

易误读：「我导入了 framework-parent 就能用 Result 了」——错，还要显式引 wshoto-framework-common。

判断2：占位 starter 是陷阱

原文依据：原文 6：config-core-starter 当前只有 package-info.java，没有 Bean、接口或自动配置逻辑。仅引用它不会获得配置加载或刷新能力

原文 12：discovery-core-starter 只有包占位，没有运行逻辑。仅引用不会注册到任何注册中心

类型：事实。怎么破：用具体的 nacos/local 实现包替代。手册专门列出这类「误以为引入就能用」的陷阱。

判断3：lane 泳道把租户映射到发布环境

原文依据：原文 15：泳道把租户映射到特定发布环境。Nacos/本地 JSON 被解析为 List<Lane>，LaneDataSourceManager 监听变化；getLaneByTenantId 找到租户则返回大写 laneId，否则返回 MASTER

租户 A 配置在 GRAY 泳道规则里，租户 B 没配置。HTTP 请求带租户 A 的 CONTEXT_JSON 进来，Feign 负载均衡会优先选实例 metadata 里 laneId=GRAY 的 Pod；租户 B 的请求会兜底走 MASTER。

判断4：trace 上下文自动透传，但线程池要用 TTL

原文依据：原文 16：普通 HTTP/Feign、框架 MQ、XXL-JOB 调用无需手工传 header；特别注意，线程池要使用 TTL 的线程池

原文 16：异常路径同样必须清理 TTL/MDC，否则线程复用会串租户、串 trace

// TTL 线程池包装 return TtlExecutors.getTtlExecutor(executor);

判断5：Redis 两层配置模型

原文依据：原文 24：真实服务采用「两层配置」：公共 Data ID redisw-info.yaml 保存连接信息，服务主配置只声明逻辑客户端映射。RunInitDefaultRedisWClient 强制要求 wshoto.redis.config.default 存在

  • Redis 物理连接：公共 redisw-info.yaml（前缀 redisw.config）
  • 服务逻辑映射：wshoto.redis.config.<client>.redisServerName
  • 默认客户端：wshoto.redis.config.default 必须存在，缺失启动失败
  • @Primary：defaultRedisWClient 自动创建为 @Primary
  • 命名客户端：用 RedisWClientFactory 显式 @Bean 声明
  • config-local 文件刷新周期：源码固定 3 秒，无 watch-interval 配置键
  • monitor 条件键：management.custom.enable（不是老版 management.metrics.custom.enable）
  • delay use-v3：3.0 必须为 true，false 不会自动回退旧协议

判断6：sharding 分片表查询必须显式带 wsTenantId

原文依据：原文 28：所有 Mapper/XML/自定义 SQL 都必须显式带 ws_tenant_id；上下文存在不能替代 SQL 条件

类型：事实（MUST）。框架提供 CustomShardingDatabaseAlgorithm 按 wsTenantId 选库、CustomShardingTableAlgorithm 选表，但 SQL 条件必须业务自己写。

判断7：EventClient 故意吞异常，不适合关键交易

原文依据：原文 23：EventClient 捕获发送异常后只写日志，不向主调用方抛出；适合非关键埋点，不适合作为交易可靠事件

类型：判断。交易事件要用事务消息或本地消息表（呼应第7章 7.7 关键消息）。

06 关键概念拆解

概念1：wshoto-framework-common（公共包）

原文术语：所有 starter 的基础包

人话解释：框架的「公共字典」。提供统一返回模型（Result<T> 成功码 00000）、业务异常层次（BaseException）、TTL 上下文（ContextHolder）、注解（@WebLog/@ExtensionPoint）、工具类（JWT/AES/RSA/SM4）。

与其他概念的关系：所有 starter 都依赖它；DTO/VO 模块只依赖它（不引 Redis/DB 重型包），避免把数据库依赖传递给调用方。

原文 5

不要误解成：异常处理器 BaseExceptionHandler 需要业务 @ControllerAdvice 继承后才生效，不是引入 common 就自动生效。

概念2：ContextHolder（上下文中心）

原文术语：TransmittableThreadLocal<Map<String,String>> 保存上下文，并同步 MDC

人话解释：一个跨线程的 Map，存 traceId、tenantId、wsTenantId、laneId、trafficType、userId 等。读取时同步到 SLF4J MDC（日志里能打 tid），TTL 回调时清理。

字段对应表：

字段/Header含义
CONTEXT_JSON完整上下文 JSON，Feign 主透传载体
x-traceId-header / tid链路与日志关联 ID
x-ws-tenant-header分库分表用的 wsTenantId
laneIdMASTER/GRAY/租户专属泳道
trafficTypeSHADOW 表示压测/影子流量

原文 5 上下文字段表

概念3：lane 泳道与发布环境

原文术语：tenantId → laneId 动态映射（MASTER/GRAY）

人话解释：公司用「泳道」做灰度发布。规则 JSON 把指定租户映射到 GRAY 泳道，这些租户的请求会被路由到灰度 Pod；没配置的租户兜底走 MASTER（生产）。

// 规则示例 [{"laneId": "gray", "tenants": ["t001", "t002"]}] // 框架读取后转大写 GRAY，未配置返回 MASTER

与其他概念的关系：HTTP 入口写 lane 到 ContextHolder；Feign 负载均衡按实例 metadata laneId 选 Pod；MQ 消费 group/tag 按 lane 路由；延时消息 header 带 laneId。

原文 15

不要误解成：lane 规则文件名要和应用名匹配，marketing 服务的规则名是 wshoto-marketingcenter-lane.json 但应用名是 marketing-center，必须显式设置 Data ID。

概念4：Nacos 配置三层组织

原文术语：namespace/group/dataId

人话解释：Nacos 用「命名空间+组+Data ID」三维度定位一份配置。公司约定：namespace=qw-${profile}（如 qw-test/qw-uat/qw-prod）、group 按职责分（DEFAULT_GROUP/LANE_GROUP/EXTENSION_GROUP/REGISTRY_GROUP）、dataId 按应用名拼。

类型namespacegroupData ID
服务主配置qw-${profile}DEFAULT_GROUP${app}.yaml
Redis 连接qw-${profile}DEFAULT_GROUPredisw-info.yaml
数据库/分片qw-${profile}DEFAULT_GROUP${app}-database.yaml
泳道规则qw-lane-${profile}LANE_GROUP${app}-lane.json
Feign 白名单qw-${profile}REGISTRY_GROUP${app}-registry

原文 34.1

概念5：Spring Cloud Stream 函数式消费

原文术语：3.0 消费端使用函数式 Bean 和 <beanName>-in-0 binding

人话解释：3.0 不再用 @StreamListener 注解。消费步骤：①写一个 MessageConsumer Bean，方法名格式【通道名】+Consumer；②用 messageConsumerWrapperFactory 包装；③Nacos 配 function.definition、binding、destination、group 四者一致。

// Bean 名 = 通道名 + Consumer @Bean public MessageConsumer echoChannelConsumer() { ... } // 通道名 echoChannel 必须与 nacos 配置一致

原文 21

不要误解成：spring.cloud.stream.bindings（设 destination/group/并发）和 spring.cloud.stream.rocketmq.bindings（设 RocketMQ 专属参数）职责不同，不能混。

概念6：sharding-jdbc 分片路由

原文术语：CustomShardingDatabaseAlgorithm / CustomShardingTableAlgorithm

人话解释：按 wsTenantId 决定数据落在哪个库、哪个表。启动时从 Nacos 拉分片 YAML，解密后落盘到 ${user.dir}/config/<app>/sharding-config.yaml，再由 ShardingSphere 构建数据源。

关键算法参数（改了=数据迁移）：tableIndex/tableLength/databaseIndex/databaseLength/tableTotal。改任何一个都会改变历史路由，必须按数据迁移处理，不能当配置热更新。

09 误解与边界

误解1：「引入 framework-parent 就能用所有能力」

为什么容易误解：parent 听起来像「继承所有」。

原文真正说了什么：framework-parent 是 BOM，只统一版本不传递依赖。每个 starter 要在 <dependencies> 显式引入。还要注意不要全引——多数 starter 会创建基础设施 Bean，错误配置会直接启动失败。

如何避免：按业务需要逐项引；mvn dependency:tree 核对最终依赖。

误解2：「引入 config-core-starter / discovery-core-starter 就有配置中心/注册中心」

为什么容易误解：名字里有 config/discovery。

原文真正说了什么：这俩是占位包，源码只有 package-info.java，没有任何运行逻辑。必须换成 config-nacos-boot-starter / discovery-nacos-boot-starter。

如何避免：看每个 starter 的「源码现状」字段；启动后看 Bean 列表和日志确认能力生效。

误解3：「Nacos 配置发布成功 = 业务已刷新」

为什么容易误解：控制台显示发布成功。

原文真正说了什么：修改可刷新测试配置后要确认目标 Bean 重绑定；数据源、连接池、第三方客户端通常不能热刷新，重要连接配置按重启变更管理。

如何避免：关键配置变更走重启流程；动态配置只用于真正可刷新的业务参数。

误解4：「分片框架会自动给 SQL 加 ws_tenant_id」

为什么容易误解：框架好像什么都能自动化。

原文真正说了什么：框架不提供透明租户隔离。ws_tenant_id 必须由业务 SQL/Wrapper 显式添加；安全检查只能发现部分危险语句，不能证明查询范围正确。

如何避免：每条分片表 SQL 都显式带 ws_tenant_id；用 SelectCheckInterceptor 辅助但不能依赖它兜底。

误解5：「NacosDeregister 能可靠地摘流」

为什么容易误解：Bean 销毁时注销听起来很稳。

原文真正说了什么：NacosDeregister 源码把占位符写成 $(spring.application.name)（注意是圆括号不是 ${}），销毁注销可能取值异常，不能作为唯一摘流机制。

如何避免：摘流要走健康检查、Service 实例剔除等多重保障，不要只靠 deregister。
