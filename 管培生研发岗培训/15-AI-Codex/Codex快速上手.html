02

零基础背景包

背景补充 Codex 是什么

OpenAI 出的 AI 编程代理：能读仓库、改文件、跑命令、执行多步任务，不只是问答。同一套能力提供桌面 App、CLI、Cloud、IDE 等多个入口。

为什么现在需要知道：本章全部内容都围绕「怎么用好这个代理」展开。

背景补充 CLI 与终端

CLI（命令行界面）是在终端里通过文字命令操作电脑的方式。适合读命令输出、逐步修改，程序员日常高频使用。

为什么现在需要知道：CLI 是 Codex 五个入口之一，「本地快速迭代」首选它。

背景补充 diff（改动对比）

把修改前后的文件内容逐行对比展示，多了什么、删了什么一目了然。代码评审的基本单位。

为什么现在需要知道：任务闭环里「检查 diff」是判断有没有越界改动的关键步骤。

背景补充 沙盒与审批

沙盒规定 AI 能写哪些目录、能不能联网、能运行什么；审批规定什么操作必须暂停问你。两者合起来限制 AI 的行动边界。

为什么现在需要知道：进阶教程的权限管理、安全边界都建立在这两个概念上。它不是本文的主张，只是帮助你读懂原文。

背景补充 MCP（Model Context Protocol）

让 AI 连接外部工具的协议，比如通过 MCP 让 Codex 操作 Draw.io 画图。启用后会携带工具信息进入上下文。

为什么现在需要知道：实战案例一（Draw.io MCP）依赖它。

05

核心判断与依据

判断1：先跑通一个入口的最小闭环，不要全配置

核心判断：入门第一原则是「选一个入口跑通最小闭环」，不要一开始同时配置 App、CLI、Cloud 和第三方服务。

原文依据（快速上手·01）：「先选一个入口跑通最小闭环，再学习其他入口。不要一开始同时配置 App、CLI、Cloud 和第三方服务。」

判断 为什么重要：把学习成本压到最低，先建立正反馈。误读：以为「全部入口都配上才算入门」。

判断2：任务六要素，不要只写「帮我优化一下」

核心判断：一个完整任务应说明目标、背景、范围、约束、验证方式和最终交付；任务越具体，越容易控制修改范围、判断是否完成。

原文依据（快速上手·07）：「不要只写‘帮我优化一下’。任务越具体，越容易控制修改范围，也越容易判断是否完成。」

判断 为什么重要：任务描述就是给 AI 的控制面。误读：把写长提示词当目标——要素齐比字数多重要。

判断3：判断任务完成不能只看最终回答

核心判断：稳定任务包含六步（写清任务→先建图→小步执行→检查 diff→运行验证→记录结果）；Codex 负责执行和整理证据，最终是否接受由使用者判断。

原文依据（快速上手·08）：「判断任务是否完成，不能只看最终回答。」「仍然需要人工 review：Codex 负责执行和整理证据，最终是否接受由使用者判断。」

判断 为什么重要：这是使用 Codex 的安全底线。误读：「AI 说测试过了」就等于测试过了。

判断4：权限越高，任务范围应越小

核心判断：权限与任务范围成反比约束：完全访问只适合范围明确的特殊本机任务、临时使用；删除、发布、支付、生产凭据必须亲自把关。

原文依据（进阶·04）：「权限越高，任务范围应越小。」「必须亲自把关：删除、迁移、发布和部署；支付、账单和权限修改；生产服务和敏感凭据。」

判断 为什么重要：防止「图省事开满权限」造成不可逆事故。误读：默认权限太烦，早点换完全访问。

判断5：上下文逐轮累积，稳定长前缀才能命中缓存

核心判断：每次请求带上的不只是当前问题，还包括历史对话、项目规则、工具定义、读过的文件等；内容过长时早期内容可能被压缩成摘要。

原文依据（进阶·01）：「上下文会逐轮累积……内容过长时，较早内容可能被压缩成摘要。」「Prompt caching：稳定的长前缀更容易命中缓存。精简 AGENTS.md，只保留需要的 Skills 和 MCP，并保持规则顺序稳定。」

事实 为什么重要：解释了为什么对话越长越「忘事」、为什么规则文件要精简稳定。误读：以为每次只发当前这句。

判断6：AGENTS.md / Skill / Plugin 各管一层

核心判断：AGENTS.md 是项目内所有任务遵守的规则（项目工作守则）；Skill 是某类重复任务怎么做（专项操作手册）；Plugin 是打包分发多种能力（可安装工具箱）。

原文依据（进阶·03 概念对比表）：「AGENTS.md：项目内所有任务遵守什么规则——项目工作守则；Skill：某类重复任务应该怎么做——专项操作手册；Plugin：如何打包、安装和分发多种能力——可安装工具箱。」

判断 为什么重要：决定你把一条经验写到哪一层。误读：什么都塞进 AGENTS.md。

判断7：手机端是跟进工具，不是决策工具

核心判断：手机远程操控适合查看进展、回复问题、处理审批；不适合大范围合并前的最终 review、生产环境操作和长时间阅读大量 diff。

原文依据（快速上手·09「不适合怎么用」清单）：「大范围代码合并前的最终 review；生产环境、密钥、账单和部署；长时间阅读大量 diff。」

判断 为什么重要：划清移动端使用边界。误读：在手机上顺手点了生产部署审批。

06

关键概念拆解

Chat（对话）vs Project（项目）

作者用法：对话适合问问题和一次性任务，不同对话相互独立、不默认共享工作目录；项目适合操作本地文件，同一项目多个对话围绕同一工作目录协作。

只问问题 → Chat ｜ 要改文件、持续迭代 → Project 原文依据（快速上手·05）：「只问问题可以使用对话；需要改文件、写代码、做文档或持续迭代时，优先选择项目。」

不要误解成：对话之间天然共享上下文——它们是独立的。

任务六要素

作者用法：目标（一句话说明结果）、背景（现象与上下文）、范围（限定文件或模块）、约束（禁止事项）、验证（命令或检查方式）、交付（如何汇报）。

原文依据（快速上手·07 要素表）。

不要误解成：六项都要写成一段话——分项写清才好核对。

AGENTS.md

作者用法：面向 coding agent 的 README，写项目结构、命令、规范和边界；按全局→项目根→当前目录逐层发现并合并，越近越具体，同目录 override 优先。

原文依据（进阶·02）：「AGENTS.md 是面向 coding agent 的 README……减少每次新对话的重复解释。」

不要误解成：个人临时偏好也往里塞——团队规则与个人偏好分开，任何规则文件都不要写 token、密钥。

Skills / Plugins / Automation / Hooks

作者用法：Skill 管「怎么做」的固定流程；Plugin 打包分发多种能力；Automation 管「什么时候自动去做」；Hooks 是生命周期扩展，在固定时机运行可审查脚本。

Skill=怎么做 ｜ Automation=什么时候做 ｜ Hooks=固定时机的确定性检查 原文依据（进阶·05–06）。

不要误解成：装了 Plugin 就自动有权限——仍受沙盒、审批和登录状态限制。

Thread / Worktree / Handoff / Subagent

作者用法：thread 是长期任务线；worktree 是并行 Git 代码工作区；handoff 负责搬移任务及其 Git 状态；subagent 是单次任务里的临时协作者。

原文依据（进阶·08）：「thread 是长期任务线；worktree 是并行代码空间；handoff 负责搬移任务；subagent 是单次任务里的临时协作者。」

不要误解成：多开线程就并行高效——后台检查频率过高反而浪费上下文。

沙盒三模式（read-only / workspace-write / danger-full-access）

作者用法：read-only 用于陌生仓库、审查、方案阶段；workspace-write 是日常默认；danger-full-access 移除本地沙盒限制，不作为日常默认。

原文依据（进阶·07 模式表）。

不要误解成：full-access 更强更好——它是给「范围明确的特殊本机任务、临时使用」的。

09

误解与边界

误解1：把 Codex 当聊天窗口，说一句「帮我看看」就够了

为什么容易误解：日常聊天习惯。原文真正说了：目录、文件、命令、验证才是高质量输入；任务要写目标、背景、范围、约束、验证、交付。原文没说：提示词越长越好。避免方法：每次发任务前对照六要素。

误解2：AI 说「已完成」就等于完成了

为什么容易误解：AI 回答语气自信。原文明确说：判断任务是否完成，不能只看最终回答；仍然需要人工 review。避免方法：检查 diff、跑验证命令、看完成标准四条。

误解3：默认权限太麻烦，早点开完全访问

为什么容易误解：审批打断心流。原文说：权限越高任务范围应越小；完全访问「不作为日常默认」；删除、发布、支付、生产凭据必须亲自把关。避免方法：先默认权限，审批频繁再考虑自动审核，长期稳定后才写自定义配置。

误解4：装了 Plugin / Skill 就自动获得了权限和能力

为什么容易误解：插件名字听起来像授权。原文说：安装 Plugin 不等于自动获得权限，仍受沙盒、审批和外部服务登录状态限制。避免方法：安装前检查来源、读写范围、外部连接和脚本行为。

误解5：第一次练习就拿重要项目目录开刀

为什么容易误解：想直接解决手头工作。原文说：不要选择包含生产凭据、客户资料、个人隐私或大量未备份文件的目录；第一个任务应简单、低风险、容易检查。避免方法：新建空文件夹做第一个任务。
