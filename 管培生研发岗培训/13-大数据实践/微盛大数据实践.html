用真实开发链路讲清楚：一句业务需求如何变成口径、血缘、任务和验证结果。本章重点：把业务话翻译成可验证的数据话。

02

零基础背景包

背景补充 DWD / ADS（承接第12章）

DWD 存一条条事件明细（谁、何时、对谁、打了什么标签）；ADS 存按维度汇总好的结果行（按日、租户、部门）。

为什么现在需要知道：本章的验证案例就是 DWD 明细和 ADS 汇总对账。

背景补充 幂等

同一个任务重跑多少次，结果都一样，不产生重复数据。靠「先删后写」或按主键覆盖实现。

为什么现在需要知道：原文收束要求「幂等」和口径、验证成套出现。

背景补充 DAG（有向无环图）

任务之间的依赖关系图：先算哪张表、再算哪张表，没有循环。调度系统按 DAG 依次执行。

为什么现在需要知道：任务设计.json 就是 DWD/ADS 的 DAG。它不是本文的主张，只是帮助你读懂原文。

背景补充 上下游对账

用上游明细的总数（或总和）去核对下游汇总的合计，两边相等才算通过，而不是「目标表有数据就算对」。

为什么现在需要知道：这是本章验证方法的核心。

05

核心判断与依据

判断1：四类需求的共同瓶颈是口径翻译

核心判断：统计报表、运营分析、AI 分析、客户交付看似不同，第一道工序都是把业务话翻译成可验证的数据话。

原文依据（第2页）：「看起来是四类需求，实际都绕不开同一件事：先翻译口径。」

判断 为什么重要：管培生接需求时的第一反应训练。误读：以为不同需求类型各有一套完全不同的方法论。

判断2：一句需求不能直接写 SQL

核心判断：「按部门统计员工给客户打标签的数量」至少有五种算法，必须先定口径再动手。

原文依据（第4页标题+导语）：「一句需求不能直接写 SQL」「至少有五种算法，必须先定口径。」

判断 为什么重要：这是「翻译」的具体证据。误读：以为这是极端案例，多数需求一句话就能写。

判断3：五种候选口径各有回答的问题，最终采用「成功新增标签事件数」

核心判断：去重客户数回答「多少客户被打过」、去重标签数回答「用了多少种标签」、组合数会合并多次动作、请求数一个请求含多个动作；最贴近「员工打标签这个动作」的是成功新增标签事件数。

原文依据（第4页表格）：五行候选口径+判断，最终采用行注「最贴近员工打标签这个动作，最终采用」。

事实 为什么重要：口径选择是「看它回答什么问题」而不是「哪个更高级」。误读：背下答案当万能口径。

判断4：目标表有数据不算通过，要对账

核心判断：验证的关键是证明明细和汇总对得上：6 行 ADS 指标合计等于上游 90 个成功新增标签事件，粒度重复为 0、空部门为 0。

原文依据（第5页）：「目标表有数据不算通过，关键是能证明明细和汇总对得上。」「验证逻辑：6 行 ADS 指标合计仍然等于上游 90 个成功新增标签事件。」

判断 为什么重要：定义了「做完」的标准。误读：跑完任务看目标表非空就提交。

判断5：harness 不替人做业务判断，而是留下判断过程

核心判断：harness 的定位是把需求、证据、任务设计和 gate 记录成可交接的工作项。

原文依据（第6页）：「它不是替人做业务判断，而是把需求、证据、任务设计和 gate 记录成可交接的工作项。」

判断 为什么重要：划清自动化边界。误读：把 harness 当全自动开发机器人。

判断6：实践的重点是说得清、查得到、跑得稳

核心判断：微盛大数据实践的重点不是写得快；口径、选表、分层、幂等、验证和 Review 风险必须成套出现。

原文依据（第7页）：「重点不是写得快，而是说得清、查得到、跑得稳。」「口径、选表、分层、幂等、验证和 Review 风险必须成套出现。」

判断 为什么重要：评价数据开发质量的标准。误读：以开发速度论英雄。

06

关键概念拆解

口径翻译

作者用法：把「按部门统计员工给客户打标签的数量」这类业务话变成明确定义的统计规则。人话：先说清「数什么、怎么数」，再写代码。

业务话 --口径翻译--> 数据话 --对账验证--> 可信结果 原文依据（第1页/第4页）：「重点：业务话翻译成可验证的数据话」。

不要误解成：简单的字段映射。

成功新增标签事件数（最终口径）

作者用法：五种候选中最贴近「员工打标签」动作的口径，被最终采用。人话：数成功发生的打标签动作次数，不数客户数、不数标签种类。

原文依据（第4页）：「成功新增标签事件数——最贴近员工打标签这个动作，最终采用。」

不要误解成：所有标签统计都用这个口径——换需求要重新判断。

粒度重复

作者用法：验证指标之一，目标粒度重复为 0、空部门为 0。人话：汇总行在「统计日+租户+部门」这个粒度上不允许出现两行。

原文依据（第5页）：「粒度重复——目标粒度重复为 0，空部门为 0。」

不要误解成：明细层也不许重复——事件明细天然可多条。

上下游对账

作者用法：DWD 事件行合计 = ADS 汇总合计。人话：下游的数必须能加回上游的总数。

原文依据（第5页验证逻辑）。

类比（仅辅助理解）：像收银台对账——卖出的每笔加总要等于钱箱里的钱。它帮助理解：总量守恒；它不能代表：逐行一致（汇总本来就是聚合）。

harness

作者用法：把判断过程沉淀为五件产物的工作流载体。人话：需求到上线的「案卷」，谁接手都能看懂当时为什么这么做。

需求.md → 方案.md → 任务设计.json → 执行计划.json → run-log.jsonl 原文依据（第6页五节）。

背景补充 gate = 流程里的检查关卡，不满足条件不放行。不要误解成：代码生成器。

链路职责边界

作者用法：数据来源、采集同步、数仓分层、分析引擎、平台自动化、业务消费六段不能混在一起讲。人话：讨论问题时先定位在链路哪一段，别串台。

原文依据（第3页）。

不要误解成：六段由六个团队各管一摊互不相干——边界是职责边界不是墙。

误解与边界

误解1：需求分类是为了记忆，AI 分析和统计报表方法完全不同

为什么容易误解：四类需求表像知识点清单。原文真正说了：四类都绕不开「先翻译口径」。原文没说：四类没有任何差异。避免方法：先找共同工序，再看差异。

误解2：成功新增标签事件数是万能正确口径

为什么容易误解：它是案例的「最终答案」。原文说的是它「最贴近员工打标签这个动作」所以被本需求采用。避免方法：口径永远跟着业务问题走，换问题重新选。

误解3：验证就是看目标表有没有数据

为什么容易误解：惯性做法。原文明确否定并给出对账标准（合计相等+粒度重复 0+空部门 0）。避免方法：提交前跑对账 SQL。

误解4：harness 会取代人的 Review

为什么容易误解：自动化听起来像免检。原文说 harness 降低漏项、口径漂移和交接成本，Review 风险仍要成套出现。避免方法：把 harness 产物当 Review 的输入。
